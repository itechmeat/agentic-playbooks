# apb 1.0.0-beta.4

The fourth beta of apb 1.0 finishes the work on the default playbooks apb
ships. Every default now carries scenarios that play its routes through the
real engine for free, a person or an installing agent can play them from
any project, a first routine outside code work ships (a read-only mail
digest), the fit report and the run say when the reviewer shares the main
role's agent, and the "update available" notice says what the shipped
content changed. The delivery playbook drops its "assessment only" label.

## Installing the beta

1.0.0-beta.4 is published as a GitHub pre-release. The `latest` release and
the Homebrew formula stay on 0.25.0, and `apb self-update` of a stable
install stays on the stable line, so stable installs are not moved to the
beta. An install of an earlier beta reaches this one through the installer
below; from this beta on, `apb self-update` of a beta install also takes
newer pre-releases of the 1.0.0 line (see "Since beta.3").

Shell installer for this tag (macOS, Linux x86_64):

```sh
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/itechmeat/agentic-playbooks/releases/download/v1.0.0-beta.4/apb-installer.sh | sh
```

From source (see `docs/INSTALL.md`, section 5; `cargo install --git` is not
supported because the web frontend must be built first):

```sh
git clone --branch v1.0.0-beta.4 https://github.com/itechmeat/agentic-playbooks && cd agentic-playbooks
(cd web && bun install && bun run build)
cargo install --path crates/apb-cli
```

To go back to the stable line, run the `latest` installer from
`docs/INSTALL.md` again.

## Scenarios for every default

- **Every shipped playbook ships a suite.** `apb-setup`,
  `apb-feature-delivery`, `apb-code-review`, `apb-research`,
  `apb-issue-triage` and the new `apb-inbox-digest` each carry scenarios
  under `evals/scenarios/`, one per route that matters: a clean panel, a
  decomposition run in order, a design that is not ready, one and two
  repair rounds, a subtask that needs a look, an empty decomposition, a
  failing reviewer, an empty issue list, comments approved and skipped, a
  judge that rejects every item, and so on. Setup installs them beside the
  playbook, and CI plays every one at quick on every change.
- **Scenario runs of a global playbook.** `apb eval <id> --scope global
  --level quick|smoke` and `apb eval <id> --scenarios --scope global` play
  and list the scenarios of a playbook in the global store, so the defaults'
  suites run from any project; MCP `playbook_scenarios` and
  `playbook_scenario_run` take `scope` too. The runs are written under the
  current project's `.apb/scenario-runs/`. A smoke run still needs the
  version trusted by its digest: a pristine default passes, an edited copy
  does not. Deep `apb eval` cases stay project-only and refuse
  `--scope global`; the dashboard's Scenarios box stays project-only.
- `docs/AGENT-SETUP.md` step 7 now plays the main default's scenarios at
  quick as part of verifying a setup, and a new "Defaults" section lists
  every default with what it does, what it needs, its effects and how to
  play its scenarios.

## A routine outside code: the mail digest

`apb-inbox-digest` reads the unread mail of one folder through the official
`imap` connector, classifies each message (action needed, reply needed,
for information, newsletter, suspicious) with a judge checking each
verdict, and writes `inbox-digest.md` in the project, grouped by category.
It binds only the connector's read-only functions (`search_messages` and
`get_message`, which never mark a message seen), so through the connector
it never marks, moves, deletes or sends mail, and it declares neither
`external` nor `irreversible`.

Message text is untrusted, and the playbook says exactly where it goes.
The listing step binds the connector, so it cannot be isolated: it runs
with the person's shell, files and network, and only its prompt keeps it
to the two connector calls. The classifying step and the step writing the
digest bind no connector and run in a sandbox where the machine has one;
without one they run like any step. A lint test keeps every later step
that reads the text isolated. Like the issue triage, the digest is refused
until the person runs `apb connector install imap`, adds an account and
approves it.

## The reviewer on the same agent

When the main role and the reviewer role run on the same agent, `apb setup
plan` and `apb doctor` said so. Now the fit report says it too, as a note
that never blocks (`same_agent_reviewer`), and a run records it at start:
`run_provenance` carries `limits`, shown by `run_status` and `apb runs <id>`
as `limit: the reviewer runs on the same agent as the main role`. One rule
in `apb_core::bundled` decides it for every surface; it compares the primary
executors only. A later profile rebind does not change what the run
recorded.

## What an update changes

The "update available" notice of a default a person changed now says how
the copy differs from the new shipped content, in one line: in the
reconcile note, the `defaults` line of `apb doctor` and the plan's
`update_available` warning, which also carries the diff itself in `diff`
with its `base` (covered by the plan digest). A playbook is compared from
the newest version that still holds apb's own shipped content (`base:
shipped`), so the person's own edits are left out and the line reads
`shipped changes: nodes +1 -0 ~2, edges +1 -0 ~0`. When every version apb
wrote was edited in place (`base: current`), and always for a skill, which
keeps no copy of the files it was installed from (`base: installed_copy`),
the diff also holds the person's own edits, so the line reads `differs
from the shipped version: ...` instead. A copy that holds a folder or file
that does not read is still compared, with that entry counted as changed.

## Feature delivery without the label

`apb-feature-delivery` 1.2.0 is named "Feature delivery". Every agent step
between the last review and the report is read-only, and a guard test keeps
it so: the report describes the candidate the panel reviewed. The review is
still the panel's judgment, the project's tests run before and after the
work, and the run still makes no commit, push or pull request. The report
step now writes its `DELIVERY REPORT:` marker into its `outcomes` output as
well, so its completion check finds it when the agent reports through the
status file. `apb-setup` 1.0.1 tells the person the mail digest needs the
imap connector.

## Since beta.3

- **Evidence freshness.** A passing script `success_check` is bound to the
  fingerprint of its declared `scope`, and the finish observes the same
  fingerprints: the run outcome shows each check as current, stale or
  unknown, and a pass that is not current is not counted as passed. Every
  evidence names its basis (executed, read, agent text, model). The scope
  is declared with the map form `success_check: { script, scope }`; V163
  refuses a scope that names no glob or one that does not compile.
- **Process skills.** `apb-diagnosis` ships for bug fixes (reproduce,
  isolate, name the root cause before a fix, then a regression test), and
  the delivery playbook runs it; `apb-review` picks its depth by risk
  (lightweight, standard, high risk).
- **The report graph.** `apb runs <id> --html` draws the definition the run
  executed as a layered graph.
- **Self-update along the pre-release line.** A stable install's `apb
  self-update` takes stable releases only, as before. A pre-release install
  also takes a newer pre-release of its own line (`1.0.0-beta.4`,
  `1.0.0-rc.1`) and any newer stable release, never a pre-release of a
  later line; when the look at the pre-releases fails, it warns and checks
  stable releases only (`docs/INSTALL.md`, "Which releases it takes").
- **Worktree entries nested under their project.** An entry of the
  projects registry that is a git linked worktree of a registered project
  is now nested under that project when the registry is listed, also when
  it was registered before worktree nesting existed or before its parent
  project was; a recorded parent is never changed by a listing.

## Fixes

- A `finish` node with a prompt took no scripted answer in a scenario run:
  it tried to start its agent, which the scenario guard refused. It now
  takes its scripted attempt like an agent node.
- A scenario run of a playbook with a node `isolation` probed the host's
  sandbox at preparation, a program start the scenario guard refused. A
  scenario run spawns nothing to isolate and no longer probes.

## Compatibility

- `run_provenance.limits` is a new optional field of a known event; older
  binaries ignore it.
- The plan digest of `apb setup plan` covers the new `diff` and its `base`;
  a plan with no `update_available` warning keeps the digest it had.
- `apb eval` takes `--scope project|global` (default `project`); the hidden
  `apb __scenario-run` takes it too.
