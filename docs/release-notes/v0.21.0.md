# apb 0.21.0

A minor release with one addition: `amocrm`, the fifteenth official connector and the second CRM after `twenty`.

## amoCRM and Kommo over REST API v4

amoCRM is a widely used sales CRM with a large, uniform REST API, and Kommo is the same API on a different domain, so one connector covers both: `base_url` is an account field, and `https://acme.kommo.com` works exactly like `https://acme.amocrm.ru` with no connector change. The surface is dense. 101 functions cover the account and its dictionaries, leads and the unsorted inbox, pipelines and statuses, contacts and companies, customers with their statuses, segments and transactions, tasks, notes, tags, entity links, the event feed, custom field definitions and groups, catalogs and products, webhook subscriptions, salesbots, lead sources, chat templates, talks, subscriptions, short links, call logging, and the Files API for listing, reading, attaching and detaching. 49 of them are `read_only` and 52 are effectful.

The count would have been closer to 160 without one decision: wherever amoCRM's routes are symmetric across families, the connector exposes one function taking an `entity_type` of `leads`, `contacts`, `companies` or `customers` rather than four near-identical ones. Notes, tags, links, custom fields, custom field groups, entity files and batch updates all collapse that way, subscriptions do too over the two families amoCRM documents for that route, and the manifest is smaller and easier to read for it.

Authentication is a long-lived token, and only that. amoCRM's OAuth2 refresh tokens are single-use with a three-month TTL, which needs token storage apb does not have; the long-lived token an integration issues from its "Keys" tab lasts up to five years, carries no refresh, and is revocable from the account. Getting one is not always a five-minute job: a private integration can require an application to amoCRM support on a non-technical account, while an external integration created directly in amoMarket issues the same kind of token without that step. Both are Bearer tokens, and the connector accepts either.

Dense coverage has a cost that is easy to miss. Every function a node is granted is rendered into its prompt in full, with description, argument schema and one example, so granting the whole connector spends 69,667 characters, roughly 17,000 tokens, before the node has done anything. `connectors/amocrm/README.md` therefore ships seven ready-to-paste grant presets (`sales-read`, `sales-write`, `inbox`, `setup-admin`, `catalog`, `customers`, `files`) alongside the measured numbers: `sales-write`, the everyday create-and-move set of 25 functions, renders 19,251 characters, about a quarter of the whole. Pick a preset, not the connector.

## What it deliberately does not do

Webhook subscriptions can be managed (`list_webhooks`, `subscribe_webhook`, `unsubscribe_webhook`) so an external receiver can be wired up, but amoCRM webhooks cannot yet be received by apb's own ingest listener: amoCRM posts `application/x-www-form-urlencoded` without a signature, and the listener requires a JSON body and an HMAC signature. File upload is absent for a similar reason, a chunked binary Drive session that no body kind in the connector format expresses, so files already in the account can be listed, read, attached and detached but not created. And every filter argument takes exactly one value, because a connector's `query` block is a map and cannot repeat a key, so `filter[id][0]` and `filter[id][1]` have no expression. All three are tracked as follow-ups against apb itself rather than worked around in the manifest.

Two more absences belong to the API, not to apb: v4 has no DELETE for leads, contacts, companies, customers, tasks, notes, tags or catalog elements, so neither does this connector, and records a playbook creates stay in the account. The eight functions that are irreversible (`decline_unsorted`, `delete_pipeline`, `delete_status`, `delete_custom_field`, `delete_transaction`, `set_customers_mode`, `enable_products`, `unsubscribe_webhook`) are named in README and in `docs/CONNECTORS.md` so a grant can leave them out on purpose.

One plain statement about how far this has been checked: the connector is documentation-verified. Every request shape is validated against the amoCRM API v4 documentation and against 107 offline contract tests that assert method, exact percent-encoded URL and request body per function, and it has not yet been run against a live amoCRM account. The live verification plan is written down in the design spec and runs when an account with an integration token becomes available.
