# apb 1.0.0

apb runs repeatable multi-step workflows for agents doing any routine with
steps and checks, code or not, defined in YAML and executed locally. One binary holds the execution engine, a visual web
editor and an MCP server your agent can drive.

1.0.0 is the release candidate 1.0.0-rc.1 with its version set to 1.0.0
and the two fixes listed under "Changes since 1.0.0-rc.1"; the code apb
runs is otherwise the same. It is the first stable release
since 0.25.0 and carries everything from the 1.0.0-beta.1 to 1.0.0-beta.7
pre-releases and rc.1.

## What 1.0 means

From this release on, apb keeps a compatibility promise for the whole 1.x
line, stated in [docs/COMPATIBILITY.md](../COMPATIBILITY.md):

1. The playbook schema (schema 2) is frozen: a definition that parses and
   validates on 1.0 parses on every 1.x with the same error codes; a field
   may be added, never removed or renamed.
2. The run journal is frozen: every 1.0 event type and field keeps its
   name and shape, a new field is optional, and a new event type is safe
   to skip up to the next checkpoint.
3. The MCP tools are frozen: a tool and an argument keep their names,
   every input a 1.0 tool accepts stays accepted, and no tool or argument
   object gains a required member.
4. Validator codes keep their meaning and severity; a retired code keeps
   its number.
5. Machine codes (reasons, refusals, run guards) keep their spelling, and
   the run files, settings files, signed stores and the playbook store
   written by 1.0 still read with the same meaning.
6. The install channels keep their names: the crate `agentic-playbooks`,
   the Homebrew formula `apb`, the release archives and `apb self-update`
   of an installer install.

A name being replaced keeps working through 1.x with a warning; removal
waits for 2.0. The promise is guarded by frozen fixtures and tests for each
area. What it does not cover (among others the CLI's text and JSON output,
the dashboard's HTTP API, scenario files and eval suites, and the Rust API
of the crates) is listed in the same document.

Linux and macOS are supported; Windows is not (on Windows,
`docs/INSTALL.md` points to WSL2 with the Linux build). Isolation `full` needs Linux with unprivileged bubblewrap; on macOS
`full` refuses with `os_unsupported` and `best_effort` runs without a
sandbox, for the whole 1.x line.

## Installing

The binary is `apb` on every channel. Details, the manual download with
verification and the source build are in
[docs/INSTALL.md](../INSTALL.md).

1. Shell installer (macOS, Linux x86_64):

   ```sh
   curl --proto '=https' --tlsv1.2 -LsSf https://github.com/itechmeat/agentic-playbooks/releases/latest/download/apb-installer.sh | sh
   ```

2. Homebrew (macOS, Linux x86_64):

   ```sh
   brew install itechmeat/agentic-playbooks/apb
   ```

3. cargo (Rust 1.99 or newer and a C compiler and linker: the Xcode Command
   Line Tools on macOS, `build-essential` on Debian or Ubuntu; no bun, the
   dashboard is inside the package):

   ```sh
   cargo install --locked agentic-playbooks
   ```

   The crate named `apb` on crates.io is an unrelated project: `cargo
   install apb` does not install this tool. The six
   `agentic-playbooks-*` library crates are internal to the `apb` command
   and not a public API.

Updating: an installer install runs `apb self-update`, Homebrew `brew
upgrade apb`, cargo the same `cargo install --locked agentic-playbooks`
again (`apb self-update` on a cargo install names that command and exits
2). Remove one install before switching to another channel.

## What you get

### Playbooks and runs

1. A playbook is a versioned graph of agent tasks, scripts, conditions,
   judges, review gates, parallel branches with joins, loops and
   sub-playbooks. Each `agent_task` binds its executor through a profile:
   agent, model, fallbacks, role prompt and skills. Built-in agents
   include Claude Code, Codex, OpenCode, Cursor Agent, Grok, Hermes,
   Qoder, Antigravity, Pi, ZCode and DeepSeek Harness (`dsh`).
2. A run survives restarts, leaves an append-only journal, and snapshots
   what it resolved into a write-once manifest. Its outcome says what was
   done, how it was verified (goal criteria, success checks, a baseline
   check), what nobody verified, and marks runs that need a look.
3. List mode runs one step per item of a list, in batches, with a check
   per item; only rejected items run again. A pilot slice can stop at a
   gate before the rest, a list can stop early, and items that passed in
   the previous successful run can be skipped.
4. Node contracts hold an agent to its job: typed and required output
   fields, a declared write scope, a check that must fail before the work,
   a stall exit for a node that repeats the same rejection, and loops that
   end when rounds stop finding new items.
5. Result snapshots keep what nodes produced, scrubbed and re-verified on
   every read; an agent can cite them, and its claims are checked as
   structurally valid or not supported, never as confirmed.

### People in the loop

1. Review gates can show earlier outputs, take typed values, withhold
   options above a size limit and bind an approval to the exact snapshots
   a person saw. A gate marked `person_only` takes a decision only at a
   terminal or in a signed-in dashboard session, and with a passkey
   enrolled it needs a fresh passkey assertion.
2. A push leaves a run only through a `publish` node, after a person
   consented to the exact plan; a push with an unknown result is never
   repeated on its own.
3. Notifications tell a person when a run waits, asks, pauses or
   finishes, with optional reminders while a wait stays open. A send never
   happens twice after a restart.
4. The fit report says whether a playbook fits a project and whether it
   is ready to run alone; unattended starts can require attended
   successful runs first (probation).

### Routines that run on their own

1. Start keys make a start happen once per event, a run deadline ends a
   run that runs too long, and a concurrency key keeps one active and one
   waiting run per key.
2. Start rules (`apb trigger`) start a playbook from the events a
   connector account receives, only after a person wrote and approved the
   rule.
3. Timer and inbox waits park the run with no driver and resume it when
   due, also after a reboot through `apb resume --all`.
4. Health rules judge a routine across its runs and can hold its starts;
   `apb runs prune` removes old runs into a signed archive.
5. A follow-up check reads the world once after a successful run, and
   `run.previous_success` lets a routine read its previous successful run.

### Cost, safety and trust

1. Estimates before a start and a predictive run budget; every surface
   shows a cost basis, and a billed-use policy can ask for a person's
   confirmation before billed agent work starts.
2. The launch policy (`agent_launch: allow | ask | deny`) decides what may
   start a run; imported scripts run only after an approval of their exact
   digest.
3. Isolation on Linux is a contract checked before every attempt
   (bubblewrap), apb's own git commands never run a program the
   repository names, and a profile can start its agent from an allowlisted
   environment.
4. Secrets are a sealed type, redacted from everything apb stores or
   sends; a secret param is never rendered into a template. An external
   data run keeps nothing for learning.

### Connectors

1. Connectors call services for a run (GitHub, GitLab, Slack, IMAP, Gmail,
   Google Calendar, Google Drive, web search and others), with send-once
   intents, OAuth refresh, bounded paging and typed inbox reads.
2. MCP tool connectors map the tools of an MCP server over stdio or
   Streamable HTTP; a person pins the program and its tools at a terminal,
   and a call whose program or tools changed is refused.
3. Eval cases can answer every connector call from recorded doubles, so a
   connector playbook is evaluated without reaching the service.

### Improving playbooks

1. Run quality grades, comparison of a candidate version with `current`,
   known problems shown to agents as facts to check, a corrections ledger
   of what people corrected, and `apb stats` across runs.
2. Scenario runs (`apb eval --level quick|smoke`) play a playbook against
   scripted answers for free; every shipped default playbook carries
   scenarios, and `apb scenario capture` turns a finished run into one.
3. Agent-first setup (`apb setup plan|apply|remove`) registers apb in the
   agent hosts of a machine and installs the default playbooks and skills;
   `apb templates` installs example playbooks; `apb discover` suggests
   playbooks from repeated work in local session history.

## Upgrading

### From 0.x

1. Playbooks of schema 1 (`executors`) convert with `apb migrate`; schema 2
   binds executors only through profiles.
2. Behaviour changes from 0.25.0, from the 1.0.0-beta.1 notes:
   1. Isolation is enforced: a node with `isolation: full` refuses to start
      on a machine that cannot enforce it, including every macOS machine;
      use `best_effort` where that is acceptable.
   2. apb's own git commands no longer run the repository's hooks, filter
      drivers, fsmonitor, external diff and textconv, pagers or credential
      helpers.
   3. A declared send whose outcome is unknown waits for a person (`apb
      intent resolve`) instead of being resent, unless the binding says
      `on_unknown: resend`. Slack and Zulip sends declare idempotency.
   4. A cut or failed read of a read-only connector function is the error
      `incomplete_response`, not a partial success.
   5. Timeouts send SIGTERM and wait a grace period before SIGKILL; agent
      output is bounded, and an attempt whose output was cut and whose
      final record is missing fails as incomplete output.
   6. `apb import` never approves an imported version automatically, and
      imported scripts need approval by digest.
   7. New validator codes; V16 is retired and V15 is listed retired beside
      it, so neither number is reused.
3. The journal stays readable by an older binary, which skips the event
   types it does not know while a checkpoint follows them. A run that uses
   a 1.0 feature carries a run guard (or a `+guard` or `+external` mode
   suffix in its manifest), so an older apb refuses to resume it while it
   can still read and stop it. Keep every apb on a machine that runs such
   playbooks at 1.0.0 or newer; `apb doctor` warns about other `apb`
   binaries on `PATH`.
4. An older apb reads a `policy.yaml` with the 1.0 sections (`runs:`,
   `health:`, `unattended:`) as invalid, refuses a `config.yaml` with
   `cloud_models:`, and cannot load connector manifests with an `mcp:`
   block or the newer manifests of `github`, `asana` and `imap`; after
   going back, reinstall those connectors with that binary (`apb connector
   install <name> --force`).

### From a beta or rc.1

1. Breaking changes of the betas, as each beta's notes state them:
   1. beta.6: a bundled reviewer that writes to a tracked file fails at
      once, and a typed output field that does not match its declaration
      rejects the attempt.
   2. beta.7: `imap.search_messages` and `imap.get_message` are marked
      `untrusted_output`, so a playbook that grants them without
      `untrusted: true` gets warning V187; a machine with a notify target
      hears about every playbook with a `health:` block.
   3. rc.1: a playbook that references a param declared `secret: true` in
      any template is refused with V340, and a run started before rc.1
      that does so is refused at resume (`secret_param_rendered`); stop it
      and start it again. A decision on a gate that uses a form feature
      names the request it answers, or it is refused `decide_again`.
   4. rc.1: an eval case of a connector playbook without full doubles is
      refused `invalid_suite` (V81 or V280).
2. A pre-release install made by the installer takes 1.0.0 with `apb
   self-update`; from then on it follows stable releases only.
3. Building from source writes the dashboard to
   `crates/apb-server/dashboard/` (before rc.1: `web/dist/`), and the
   development commands of the six libraries name their packages
   (`cargo test -p agentic-playbooks-core`; `cargo test -p apb` stays).

## Changes since 1.0.0-rc.1

1. Crate publication: the last step of the publish workflow, which
   installs the published crate and checks `apb --version`, failed after
   a passing check on rc.1 because its cleanup read a variable that no
   longer existed. It now exits 0 after a passing check, and a test runs
   that step against stubs.
2. Install docs: `docs/INSTALL.md`, the crate README and the project
   README name 1.0.0 as the current release; a release candidate is still
   installed with cargo only by its `--version`.
