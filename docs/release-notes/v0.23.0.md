# apb 0.23.0

A minor release. A playbook's goal criteria are now checked when a run reaches its finish node, an `agent_task` can protect files from its own attempt, every run leaves a trail from its commits back to itself, `apb stats` measures a playbook version across its runs, and a new host execution mode lets the agent that started a run execute its agent steps with its own subagents instead of apb spawning agent CLIs. It also carries everything prepared for 0.22.1, which was never released: a projects registry an older or newer apb cannot parse is never overwritten, a self-loop edge loops, and a set of smaller fixes. The playbook schema stays at 2: every new field is optional, and a playbook, profile or config without them validates, runs and journals exactly as in 0.22.0. The changes that need attention are under "Upgrading".

## Goal criteria are checked at the end of a run

Until now `goal.criteria` was a declared contract that nothing evaluated. When a run reaches a finish node, after every node before it has run and after the finish answer is composed, the engine now checks each criterion: a `script` criterion runs a script under the version's `scripts/` (covered by the trust digest) with `sh` in the run's working tree and the run context in its environment, and passes on exit 0; a `marker` criterion passes when its literal string appears in the finish answer or in the latest output of any node; a `manual` criterion is listed as an item for a person to confirm. Each criterion journals one `goal_checked` event with its status (`passed`, `failed`, `manual`, or `error` when the check could not run) and a detail.

By default the results are only reported. `goal.enforce: true` turns a failed `script` or `marker` criterion into a failed run with a `run_error` naming it, and V41 warns when `enforce` is set while every criterion is manual. `run_status`, `run_report`, `apb runs <run>` and the dashboard run page show the goal with each criterion's result, `pending` until the run is checked; `run_report` shows the evaluated goal instead of the unevaluated copy it carried since 0.20.0. Because the checks run after cleanup nodes, criteria should test persistent outcomes (a pushed branch, a file in the repository, a passing test suite), which `docs/HOWTO-authoring.md` now says. A run that ends before a finish node checks nothing, and a playbook without criteria journals and reports as before.

## Protected paths

`protect: ["tests/**", "docs/spec/*.md"]` on an `agent_task` names files an attempt must not change, relative to the node's working directory. Before every attempt the engine copies the matching files into the run directory; after the attempt's process has ended it lists them again. A file that was modified, deleted or added is restored from the copy (an added one is removed), the change is journaled as one `protected_paths_modified` event, and a reported success is rejected with `protected path modified: <path>`: an ordinary retry that keeps the report as `rejected_output`, like a failed success check. The retry and every later node therefore start from the files as they were, without a separate worktree.

The check runs after the attempt, not inside the agent, so it works for every agent and in host execution mode: it cannot stop a write, only reject and undo it. On a git tree, paths git ignores are never protected, and `.git` and `.apb` are never covered. V75 refuses a glob that is empty, absolute, climbs out with `..` or does not parse; V76 (`apb validate`, `apb doctor`) warns when a glob matches no file in the project. A node without `protect` is not checked and journals as before.

## Run provenance

Every `agent_task` process now gets `APB_RUN_ID` next to `APB_RUN_DIR` and `APB_NODE_ID`, script nodes get all three, and a prompt can place the id itself with `{{run.id}}`. On a git tree the engine reads `HEAD` before an `agent_task` or `script` node and again when it finishes; when `HEAD` moved, it journals one `artifacts_committed` event with the node's commits (newest first, at most 50 listed) just before the node's `node_finished`. `run_status`, `run_report`, `apb runs <run>` and the dashboard run page list the commits per node. A tree without git or without a commit records nothing.

For the other direction, `docs/HOWTO-authoring.md` ("Linking runs, commits and tracker records") documents an `Apb-Run: <run id>` commit trailer, so `git log --grep` finds a run's commits and a tracker record can carry the run id. The repository's own `apb-task-implement` 1.16.0 asks for the trailer.

## apb stats

`apb stats [--playbook ID] [--since 30d] [--compare VERSION] [--all-projects] [--json]` computes workflow metrics from the run journals alone: it asks no model and writes nothing, and like `apb decisions report` it reads only runs this installation created. Per playbook version it reports run outcomes, first-pass runs (succeeded with no retry, fallback or loop traversal), retries, fallbacks and bounded-edge loop traversals per run, gate and question waits, run duration, tokens and reported cost per run, missing deliverables and output fields, and each goal criterion's results; per node, its first-pass rate, retries, re-entries and duration against its `expected_duration`. Every rate is printed with its count, and a version with fewer than ten runs carries a note that the rates are indicative only. `--compare` sets one version next to the latest other one with the differences. A step handed to the host by the execution fallback counts as a fallback.

The dashboard shows the same report per version on a playbook's page (Stats), from `GET /api/stats`. `docs/STATS.md` documents every figure and the JSON shape.

## Host execution mode

By default apb executes every agent step by spawning the agent CLI the node's profile names. In host execution mode (informally "mono-agent" mode) apb spawns no agent CLI at all: every agent step becomes a host task that the agent which started the run executes with its own subagents. The agent passes it only when the person explicitly asks (mono, host or single-agent mode, or "use your own subagents"), for example because a subscription-bound desktop agent's second CLI process would run outside the person's session; the agent never picks it on its own. The one automatic path is the fallback below, for a step whose CLI cannot start at all. Nothing in apb detects a host by name; `cli` stays the default, and there is no machine or dashboard switch that turns host mode on.

The host passes `execution: "host"` on `playbook_run`; the run starts in the background. `run_wait` returns `reason: needs_input`, `needs: host_task` and `pending_tasks`, one entry per waiting step with the full prompt (the rendered node prompt plus apb's report contract), the profile's role prompt, the paths of the skill copies materialized from the run snapshot, the working directory, the environment the step expects (`APB_RUN_DIR`, `APB_RUN_ID`, `APB_NODE_ID`, `APB_STATUS_FILE`), the outputs contract, the deadline and a model hint. The host runs each task with a subagent and hands the final reply back verbatim with the new `run_task_submit` tool (`succeeded`, `failed`, or `blocked` when the subagent needs the person, which parks the run on an ordinary question). The engine treats a submission exactly like a finished CLI attempt: report parsing, the status file, `success_check`, `require_verdict`, the completion check, `protect`, retries, fallbacks, loops, gates, sub-playbooks and resume all work unchanged. `supervisor_wait_event` returns `reason: host_task` for a session supervising its own run. The protocol lives in the tool descriptions and in `playbook_howto`; the tier-0 instructions are unchanged.

Host mode changes who executes, not what is allowed: the run gate (trusted playbook and profiles, effects consent) is the same, the prompt is rendered from the trusted snapshot, the host never receives a connector secret, and every submission is journaled as `host_task_submitted` with the MCP client's name. A profile's agent, model and invocation settings are ignored in host mode; fallback and tier models become model hints; the role prompt, skills and node contracts stay in force (`docs/PROFILES.md`). A host run's agent steps are cached under agent `host`, so host and CLI outputs never share a cache entry.

A second, automatic path covers background and supervised `cli` runs an MCP host session starts: when none of a step's CLIs can start at all (the binary is missing or not logged in), that one step is handed to the host and the journal records `execution_fallback`. Ordinary agent failures never fall back. `execution.fallback_to_host: false` in the global or the project config turns the fallback off, and `APB_EXECUTION=cli` forces `cli` without a fallback; a project can never turn host mode or the fallback on.

Other surfaces: `apb run <id> --execution host`, `apb tasks [run]` to list pending tasks and `apb tasks submit <run> <task_id> --status ... --output-file <file>` to answer one from a script; `apb doctor` and `playbook_adopt_report` state the default and whether the fallback is on; `run_status` carries the run's `execution` and `pending_tasks` for a run that has an execution block; the dashboard run page shows a read-only host mode or host fallback badge, a Host tasks card with each pending task and its prompts, and the request, submission and fallback rows in the timeline. `docs/HOST-INTEGRATION.md` has the whole protocol and when an agent should choose the mode.

## Review auto-decision reads declared effects

V73 found a shipping step after an `auto_decide` gate by the node's name only. It now reads the strongest evidence first: a new optional `effects` list on every node (declaring `irreversible` or `secrets` refuses the auto-decision whatever the node is called), then a granted connector function flagged `irreversible: true` in its connector definition (a new optional flag), and only then the name heuristic. A granted function that is merely not read-only gives a V73 warning naming it. `auto_decide_ok: true` still overrides, and the run-time check at the gate uses the same rule with the installed connectors' facts. A node's declared effects also widen the playbook's effective effects.

## Decision report labels for two more uses

`apb decisions report` now labels `review_triage` by the person's decision at the same gate visit and `retry_advice` by the next attempt of the same node on the same agent and model. A recommendation the reviewer was shown (advise or enforce) is reported on its own "shown to the reviewer" line and kept out of every figure, because agreement with advice one has seen is a biased label; the JSON report gains `shown_to_reviewer` only for groups that have such decisions. Visits the model decided itself, fallbacks, other models and enforced skips stay unlabelled.

- `docs/GUARDRAILS.md` maps every apb construct to the layer it controls and says whether it advises or enforces. It records a measurement: the hooks in a project's `.claude/settings.json` still run for a claude node on the minimal environment; only user-scope settings and hooks stay out. `docs/PROFILES.md` no longer implies otherwise.
- `docs/CI.md` covers running apb in GitHub Actions and on a generic runner around `apb run --detach` and `apb wait` with its exit codes, the config directory and credentials on a runner, trust when no person starts the run, `--worktree` and gates.
- A new read-only example, `examples/playbooks/ci-failure-triage.yaml`, turns a build log into `failing_step`, `likely_cause` and `next_action`. Every example playbook now declares a goal with a marker criterion and manual criteria for what only a person can confirm.
- `docs/HOWTO-authoring.md` adds that a review finding seen a second time belongs in the project's memory file, and how runs, commits and tracker records link both ways.

## The projects registry survives an older dashboard

When two apb builds share one config directory, an older build that could not parse `projects.json` treated it as empty and wrote the empty registry back, and every registered workspace disappeared from the dashboard. The ordinary way to get there was an in-place upgrade from 0.20.x or 0.21.x to 0.22.0 with the dashboard service still running on the old binary: 0.22.0 had dropped the per-entry `name` field that the older reader requires, while `schema_version` stayed at `1`. (#177)

A registry file that exists but does not parse, cannot be read, or carries a `schema_version` newer than the binary knows is now never written. Listings and lookups answer from a read-only view of it, every writer refuses (`apb projects remove` exits with the reason), and the reason is logged once per process. Fields this build does not know, on the file and on each entry, are kept on every write. Entries carry `name` and `playbook_count` again, computed at registration as 0.20.x and 0.21.x did, and entries a 0.22.0 build left without `name` are filled in, so a still-running older dashboard keeps parsing the file. `schema_version` is now `2`: a version-1 file is read as it is and upgraded once on its next access, and a later format change will make this build refuse to write rather than downgrade. (#177)

The older binaries themselves cannot be fixed, so the damage they can still do depends on the file they find. Upgrading from 0.20.x or 0.21.x to 0.22.0 with the dashboard running can empty the registry; upgrading straight to 0.23.0 cannot, because every file 0.23.0 writes stays readable by the old dashboard. A registry emptied by an earlier upgrade stays empty: run any registering command (for example `apb runs`) inside each workspace to register it again. Stopping or restarting the dashboard when the binary is replaced remains the simplest habit. `apb doctor` now reads the running dashboard's version from `/api/health` and warns when it differs from the binary, which is exactly the state in which the damage happened. (#177)

## A self-loop edge loops

A node whose loop edge points straight back at itself (`review -> review`, bounded by `max_traversals`) failed the run on its first pass with "has no outgoing edge and is not finish", although the validator accepted it and a `fallback` edge was wired. The frontier dropped the node it had just finished, so the selected self-edge led nowhere. (#171)

A selected self-edge now re-enters its node like any other loop edge: each pass is a counted `edge_traversed review -> review`, the node runs again, and once the cap is spent the run takes the fallback edge. A self-edge whose condition stops matching earlier ends the loop there. Resume after the looping node and self-loops inside parallel branches behave the same, and a `judge` self-edge gets its own answer for every execution. `docs/HOWTO-authoring.md` ("Bounded loops") shows the pattern. (#171)

## Also fixed

- The review auto-decision of a gated run weighs the sub-playbook versions the run's gate pinned, the versions it will execute, instead of whatever version is current when the gate is reached. A child re-versioned mid-run no longer changes the verdict in either direction. (#178)
- A `playbook_catalog(query)` for another workspace applies the stricter of the calling project's and the target project's decision settings, so a project that switched catalog ranking off is never ranked on behalf of another one. (#178)
- `apb decisions report` and `apb decisions replay` read only run directories apb created on this machine (their origin stamp verifies), so a journal that came with a repository is neither counted nor replayed. The number skipped is printed on stderr. (#178)
- The catalog-ranking daily-cap lock lives as long as the provider chain can legitimately hold it (`timeout_ms` times the number of providers plus ten seconds) instead of a fixed minute, and an abandoned lock is broken with a `stale_lock_broken` note in `decisions.jsonl`. (#178)
- `apb doctor` checks each decision provider with one request that costs nothing, sent with its key to its own base URL within `timeout_ms`, and reports the HTTP status and latency or the timeout. A connect alone had reported a provider as reachable while it hung every request. Providers with a command-produced key keep the connect check, labelled "connect only". (#178)
- A detached driver re-exec'd from a binary that was just rewritten waits out a short "text file busy" window instead of failing to start. (#178)
- Five tests that failed under a loaded host no longer depend on timing: they wait for the state they need (a node held until the test releases it, a pending review, a listener's own readiness banner, the dashboard's own port claim) instead of racing it. (#178)
- `run_wait` names the channel of a `needs_input` answer in `needs` (`question`, `review`, `supervisor` or `host_task`).
- `docs/DECISIONS.md` names the release each use shipped in, `CHANGELOG.md` points to `docs/release-notes/`, and the README states the current release line. (#178)

## Upgrading

- **Journals.** Runs written by 0.23.0 can contain six new event types: `goal_checked`, `protected_paths_modified`, `artifacts_committed`, `host_task_requested`, `host_task_submitted` and `execution_fallback`. Each is safe to skip up to the next checkpoint, so every binary from 0.22.0 on skips them: it can read and stop such runs, and resume them wherever a checkpoint follows every unknown event. 0.21.0 and earlier cannot read them. A plain `cli` run of a playbook without goal criteria or `protect`, outside a git tree, journals exactly as in 0.22.0.
- **Host runs and older binaries.** A 0.22.x binary does not know the manifest's `execution` block and ignores it. It may therefore resume a host-mode run that is parked between nodes, and it then continues that run as a `cli` run, spawning the CLIs the profiles name. A run parked inside a host task is refused, because no checkpoint follows its `host_task_requested`. Resume host-mode runs with 0.23.0.
- **New fields need this version.** Playbooks with `protect` or `effects` on a node or `goal.enforce`, connector definitions with a function flagged `irreversible`, and a `config.yaml` with the `execution` section are refused by an older apb, which rejects keys it does not know.
- **Goal criteria now run.** `script` and `marker` criteria that were only recorded are now evaluated when a run reaches its finish node, and their scripts run in the run's working tree. They only report unless `goal.enforce: true`. `run_report` shows the evaluated goal in place of the unevaluated copy.
- **V73 is stricter.** A playbook whose `auto_decide` gate is followed by a node declaring `irreversible` or `secrets` effects, or by a node granted a connector function flagged `irreversible: true`, is refused where the name heuristic alone let it pass. Set `auto_decide_ok: true` on the gate when that is intended.
- **Host fallback is on for MCP-started background runs.** A background or supervised `cli` run started over MCP hands a step whose CLIs cannot start at all to the calling session instead of failing it. Turn it off with `execution.fallback_to_host: false` in the global or project `config.yaml`, or with `APB_EXECUTION=cli` for a process. CLI and dashboard starts never fall back.
- **Trust.** The repository's own `apb-task-implement` 1.16.0 is a new version, so its trust has to be granted again before it runs.
- **Projects registry.** `projects.json` is written with `schema_version: 2`; 0.20.x and 0.21.x still read it, through the `name` and `playbook_count` fields it keeps writing for them. Upgrade from 0.20.x or 0.21.x straight to 0.23.0 rather than through 0.22.0 while a dashboard is running.
