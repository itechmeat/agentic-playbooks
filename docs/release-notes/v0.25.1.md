# apb 0.25.1

A patch release. `apb resume --from-node` no longer starts a join whose
other branch the resume brings back to life, and a supervisor retry of a
failed parallel branch no longer does either. (#203)

## Joins wait for a re-run branch

A run failed in one branch of a fork, so its join wrote that branch off
(`join_input_dead`) while the other branch had already delivered. Resuming
the run from the failed node then started the join in the same moment as
the re-run node: the join was weighed against the old pass, in which the
re-run node was still failed and routed away. In the field case the join
ran, and so did the import step after it, before the revived branch had
produced anything. In a second shape, where the join had already run on the
first pass, the run ended `succeeded` through the join's old route into its
finish node, without running the join again on the new input.

A drive that executes a node again now treats that node and every node only
downstream of it as not yet run for routing, from the moment it starts until
each of those nodes runs again. The view lives in the journal, so every later
decision sees it: each advance, the end of a parallel batch, a later resume.

- A join fed by the re-run node's branch waits until that branch arrives,
  then runs with the normal readiness check.
- If the branch does not deliver (the node fails again, or routes
  elsewhere), a join that never ran is weighed again and journals a fresh
  `join_input_dead`, exactly as in a first pass. A node that already ran in
  the earlier pass (a join, a `join: any`, a merge inside a cycle) is not run
  a second time on the same old inputs; it runs again only when the re-run
  branch delivers into it.
- An old route of a downstream node is not taken again: the run reaches its
  finish node through the join's new execution.
- Nodes upstream of the re-run node keep their state, and inside a loop the
  nodes that lead back into it keep their routing and stop the revival: a
  sibling branch that never started is still waited for, one that already
  completed is not re-run before the loop comes back to it, and a
  first-arrival merge inside the cycle still runs on an earlier arrival.

This applies to an explicit `apb resume --from-node` (`run_resume` with
`from_node`) and to a supervisor's directives: `supervisor_node_retry`,
`supervisor_run_continue_from`, a patch, and a move off a review gate, after
a single failed node or failed members of a parallel batch. An automatic
restart of interrupted work (after a crash or a `--now` pause) revives
nothing, because the nodes after it may already have run in this pass and
their routing is real. Siblings a fork's failure policy cancelled when the
re-run node failed are revived with it. A requested re-run that a pause or a
crash stopped before it began (the re-run node had not started, or a revived
review gate was still waiting) is re-run by the next resume; several such
re-runs are each run once, never by re-running an unrelated last node. A
later re-run upstream of an earlier owed one takes it over; one asked inside
an owed re-run's revival (a `--from-node`, or a supervisor's retry or
continue-from) is refused before anything is journaled, naming the owed
node to resume or re-run from instead. When a
supervisor moves the run away from a failed node, that node's own failure
route (a rollback, say) is not taken. A `defaults.on_failure` handler is
revived with the nodes it covers. `run_answer` reports the finish the run
reached last, and nothing while a revived finish has not been reached again.

## `nodes_revived` and `join_input_revived`

Two new journal events record the revival. `nodes_revived` (`from_node`,
`nodes`) names the re-run node and the nodes it revives; the run's history
(`run_status`, reports, stats) keeps their earlier results until they run
again. `join_input_revived` (`node`, `sources`, `from_node`) names each join
whose earlier write-off no longer holds and the inputs it waits for again.
Both are written before the re-run node starts, and the dashboard's run
journal shows a note for them and for `join_input_dead`. A fresh run never
carries either.

Older apb versions skip both events. `join_input_revived` carries no state;
without `nodes_revived` an older apb routes a revived run the way 0.25.0 did,
which is this bug, not a corrupt run. A run revived by 0.25.1 must therefore
not be driven by 0.25.0 or older, and a run whose driver was killed between
the revival and the re-run node's finish must be resumed with 0.25.1 or
newer. The reverse is safe: every node an older apb ran leaves the revival
on its own start or finish, so 0.25.1 resuming after it routes correctly.

## Known limitations

- A node's earlier failure that the re-run never visits again can still end
  the run failed: the unhandled-failure check reads the whole journal, as it
  did before.
- When a supervisor moves the run away from a failed node, its failure route
  is left out of that drive's frontier, but not durably: a later resume that
  rebuilds the frontier from the journal can still offer it, as before.
