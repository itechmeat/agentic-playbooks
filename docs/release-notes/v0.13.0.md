## apb 0.13.0: batch workers get a clean room

This release was written by its own field reports. A real five-phase playbook ran against a production monorepo and surfaced an entire family of ways a run can die between an agent finishing its work and the engine hearing about it; then, while the fixes were being developed with the very playbook they improve, one of those failure modes fired live and killed a run mid-orchestration. Everything that broke is now either fixed or has a named issue, and the fixes shipped here were dogfooded by the runs that followed.

The headline is hermetic agent invocation. Node agents are batch workers, not interactive sessions, yet they inherited the user's personal Claude Code plugins and hooks, and a globally installed Stop hook could demand one more reply after the agent had already reported, turning that extra reply into the node's final output. A profile can now declare `hermetic: true`, and apb spawns the agent with an apb-owned minimal settings profile that disables user-scope plugins and hooks. The flag is snapshotted into the run manifest like the rest of the profile, agents whose adapter has no such mechanism warn and proceed, and every write path that touches profiles, the MCP `profile_write`, `apb profile edit` and the dashboard API, now round-trips the flag instead of silently resetting it, a data-loss class the release's own review caught twice.

The attempt verdict no longer depends on the least reliable byte stream there is, the agent's last words. Every agent_task attempt gets an `APB_STATUS_FILE` environment variable pointing at a per-attempt JSON file in the run directory; the agent writes its status and named outputs there, the engine reads the file before any text parsing, and the marker form stays as the documented fallback. A stale file from a previous execution is removed before spawn so a continued run can never read a ghost verdict. And when a success report is rejected by a marker check, the rejection now consumes a retry like any other failure instead of bypassing `max_retries`, while the discarded report text survives as `nodes.<id>.rejected_output` for whatever runs next, because a step that was cut off and a step that found nothing are very different inputs for a recovery node.

Two smaller robustness holes closed alongside. `apb runs` and the MCP runs listing now fold status through the same driver-liveness path the doctor uses, so a healthy run driven from another terminal is never listed as interrupted. And when an agent_task prompt advertises a bound connector that has no configured accounts, the prompt now says plainly that calls will fail until an account is added and points the agent at the fallback path, instead of listing an empty accounts line the agent discovers by failing. The duration parser also learned compound values, so `1h30m` validates instead of forcing authors into `90m`.

The dashboard grew a shared project filter. Listings used to render every project's entries in one flat grouped wall; now a selector above the list filters to one project, All projects reproduces the old view and remains the default, the choice persists in localStorage across visits, and the playbooks and runs pages share one store so switching pages keeps the selection. In the visual editor, the auto-layout stopped tangling multi-output nodes: successors are placed in the same left-to-right order as the source outputs, so a simple fan-out no longer crosses its own edges. A layout the user arranged by hand is now marked as such and automatic reflow refuses to touch it; only the explicit re-layout action overrides the marker, and layouts saved before this release are treated as not user-arranged.

The finish-node closing summary got the same discipline as everything else in this release. The composer used to receive the run instruction framed like work to execute, and one confused composer dutifully re-derived the whole task, found it already merged, and reported failure at composing its own goodbye. The instruction is now quoted reference context, the composer's sole deliverable is a closing message, and its output is treated as text, so it can no longer fail the composition by trying to be helpful.

The MCP server moved to rmcp 3.0.1 with wire compatibility for old-revision hosts preserved and verified against a scripted 2025-06-18 stdio client. Supervised-run feedback fixes landed with it: the run-start policy warning when a bound connector has no accounts, a tightened node output contract, `playbook_get` serving a compact summary interface sized for MCP injection instead of a 90KB payload, and instruction precedence over stale playbook prompt text. The repository also records its position on the MCP 2026-07-28 revision, and the project's own development playbook moved to 1.13.0 with prompt fixes shaped by the same supervised runs.

Beyond the fence, the first Buzz integration shipped as an example: an apb-operator persona pack that gives a Buzz-resident agent the apb MCP server, so a channel conversation can list playbooks, start approved runs, relay human-review gates into chat and report results, plus a recipe documenting the setup path that actually works on current Buzz desktop builds.

Gates green throughout: fmt, clippy with warnings denied, the workspace test suite, code-ranker with no violations, the frontend check, 384 frontend tests and the production build.
