# apb 0.24.3

A patch release. A playbook can now learn from one run for the next ones: a supervisor writes a forward patch, later runs try it as a candidate, and success promotes it. Host mode gets sanctioned decision-model calls inside host tasks, prompts handed over by path, and the model each attempt actually ran on is shown on every run surface. (#192, #193)

## Learn across runs (#192)

### Forward patches

`supervisor_patch_playbook` takes a new `scope`:

- `current_run` (the default) works as before: the patch may change only nodes that have not run yet, and the run migrates onto it.
- `next_runs` writes a patch version for later runs. It may change any node, including the ones that already ran. The current run keeps its version: no migration and no continuation point.

A forward patch records its provenance in `meta/<version>.yaml`: `created_by: supervisor`, `run_id`, `classification`, `scope: next_runs`, `base_version`, a `rationale` and an `evidence` list. Its guards:

- The validator and `max_patches_per_run`, as for in-run patches.
- `workaround` is refused: it has no meaning for later runs.
- It may not change the goal, the declared effects, effective effects (secrets, irreversible effects, new scripts), `requires`, the `supervisor` block, connector grants, sub-playbooks, `worktree`, or the decision opt-ins in `defaults` (`host_decisions`, `retry_advice`). Binding a node to another profile stays allowed, since profile trust is checked at every run start.
- It must be based on the playbook's `current` version or on the candidate under trial (`stale_base` otherwise), so a forward patch can never undo a version a person saved in the meantime.
- It is accepted while the run is live and for 30 minutes after it ends. A run whose driver died counts as ended at its last journal line.

### Candidate versions and trials

A forward patch becomes the playbook's `candidate`, a pointer next to `current`. There is one candidate at a time. A newer forward patch based on the candidate replaces it and keeps the lineage. A version saved or promoted by a person ends the trial.

- **Who runs it.** The policy `supervisor.policy.trial_candidates` decides whether a run started without an explicit version uses the candidate: `next_run` (the default), `off`, or `{ share: p }` for a random share of starts.
- **Trust.** The candidate runs under the trust of `current`, the same way an in-run supervisor patch runs under the trust of the version its run started on. When that does not hold, for example when `current` itself is not approved or the candidate's profiles do not pass the gate, the start falls back to `current` and reports `candidate_skipped`. An acknowledgement, explicit or implied by a CLI or dashboard start, never covers a candidate.
- **Promotion.** `promote_supervisor_patches` applies: `on_success` and `always` promote on the first successful trial, `after_n_successes: N` on the N-th, `manual` never.
- **Rejection.** A failed trial, or a goal criterion that does not hold, drops the candidate and journals `candidate_rejected` with the run id. A promotion journals `candidate_promoted`.
- **Where it shows.** `run_status` (`candidate_trial` with its verdict, or `candidate_skipped`), `playbook_get` (`candidate` with its provenance), `apb runs` (a list column and a detail line), `apb stats` (`candidate_trials` per version), and the dashboard: a run-list badge, a card on the run page and a badge in the version history.

### Retrospective context

- **New MCP tool `run_retro_context { run_id, compare_last? }`.** It returns a run's numbers so whoever improves the playbook does not have to re-derive them from the journal. Per node: time against `expected_duration`, executions, re-entries, retries, fallbacks, tokens and cost, the model actually used, the host wait (`host_task_requested` to `host_task_submitted`), and the status-file verdicts. Per run: the goal results and a comparison with the median of the last N runs of the same version.
- **Template variable `{{run.retro}}`.** It renders the same report as compact text for a prompt, capped at 8 KiB.
- **Retro pattern.** `docs/HOWTO-authoring.md` describes a final `retro` agent node: it reads `{{run.retro}}` and the run's artefacts and writes findings, each with evidence and a target. The supervisor turns accepted findings into forward patches.

## Host mode (#193)

### Decision calls inside host tasks

The host execution contract now allows bounded decisions inside a host task: choose, rank, filter, map, yes/no and score, asked of the configured decision providers. That is not running the task elsewhere. The contract is still rendered from one source, so every surface shows the new text.

- **New CLI `apb decide <kind> "<question>"`** with `--option`, `--item`, `--criteria`, `--run`, `--node`, and **new MCP tool `decision_ask`**. Both use the providers, budget and redaction of `decisions.yaml`.
- **Journaled in the run.** With a run (from `APB_RUN_ID` in the task environment, or `run_id`), the call is journaled as `decision_made` with `use_site: host_task`, the node, provider, cost and latency, and the run's budget applies. Outside a run, a call is logged in the project and capped per day.
- **Refusals.** A call is refused with a clear reason when no provider is configured, the budget is spent, `APB_DECISIONS=off` is set, the use is switched off, the playbook opts out, or the run has ended.
- **On by default.** `uses.host_task` is on once a provider is configured. A playbook can opt out with `defaults.host_decisions: off`.
- **Reports.** `apb decisions report` groups the `host_task` use.

### Prompts by path

- **Paths on every task.** Every pending host task carries absolute `prompt_path` and `role_path`, and the contract tells the host to pass the prompt to its subagent by path instead of copying it.
- **Leaner `run_wait`.** `run_wait` and `supervisor_wait_event` take `inline_prompt` (default `true`). With `false`, they return the paths only.

### The model actually used

The model each attempt ran on is now shown next to the profile's primary model: CLI attempts from the agent they started, host attempts from the model the host reported (`unreported` when it named none).

- `apb stats`: models and `model_mismatch` per version and per node.
- `run_status` and `run_report`: `attempt_models` and `model_mismatch`.
- `apb runs <id>`: one model line per attempt.
- The dashboard: a Models panel on the run page and a models row in the stats card.
- `apb doctor --run <id>`: a warning for each mismatch.

Model names match when their tokens agree up to version numbers and vendor words, so `opus` matches `claude-opus-4-1`, while `glm-5.3` and `glm-5.3-flash` count as different models.

## Fixes

- **The event log is safe against concurrent appends.** Each event and its newline go out in one write, under a file lock that also covers assigning the next seq. Two processes appending to one run, such as the drive and an `apb connector call` or `apb decide` from a task, can no longer tear a line or reuse a seq.
- **The run's decision budget holds under parallel calls.** A decision reserves its slot before the request is sent, and the drive counts the decisions host tasks made.
- **Agent detection runs outside the workspace.** `apb doctor`, the profile editor and every other agent-detection probe now start each agent CLI from the filesystem root, not from the project. `opencode models` reads project config and starts the MCP servers it names, so detection in a cloned repository could run that repository's commands, and a nested `apb mcp` registered the directory in the machine-wide project registry. A local test run left dozens of `/tmp/.tmp*` entries there this way.
- **The ZCode desktop app is no longer taken for its CLI.** On Linux the desktop package links `zcode` on PATH to the Electron app, and probing it with `--version` booted or woke the desktop. Detection and the default launch program now skip the desktop app and use the headless CLI that ZCode deploys in the home directory.

## Compatibility

Every change is additive:

- **New events.** `candidate_promoted` and `candidate_rejected` are always followed by the `run_finished` checkpoint, so an older binary skips them.
- **New fields.** The new manifest, provenance and event fields are optional, so existing runs, manifests and version sidecars read unchanged.
