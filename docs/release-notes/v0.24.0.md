# apb 0.24.0

A minor release. The `irreversible` effect is now enforced instead of only listed: a run whose playbook tree declares it starts only with an explicit consent, which the run manifest records. `apb eval` runs a playbook's eval cases in disposable repositories, stores the pass counts per configuration and compares them with the previous result. `apb runs <run>` shows the run's execution mode and prints the MCP `run_status` object with `--json`. The playbook schema stays at 2: every new field is optional, and an unconfigured run of a playbook without `irreversible` effects validates, runs and journals exactly as in 0.23.0. The changes that need attention are under "Upgrading".

## Irreversible effects need a consent at run start

Until now `effects: [irreversible]` was shown on the consent screens and read by V73, but nothing stopped a run that declared it. A run whose effective effects include `irreversible` (the playbook's own, its nodes' and every sub-playbook's, recursively) now starts only with an explicit consent. The engine checks it while it prepares the run, before anything is written, so no launch surface can skip it; the run gate returns the same refusal earlier as structured JSON: `irreversible_requires_confirmation`, naming the sources that are irreversible and how each surface consents.

Who consents: an MCP host that passes `acknowledge_untrusted: true` on `playbook_run` or `playbook_execute_plan` after asking the person (`by: mcp` or `mcp:<client>`); a person typing `apb run` at an interactive terminal (`cli`); a script author writing the new `apb run --confirm-irreversible` (`cli_flag`), which is the standing consent of a CI step; a person confirming the dashboard's Run dialog (`dashboard`), which now lists the playbook's irreversible sources before it starts the run. A trigger, an event bridge posting to the dashboard API, or a headless start without one of these is refused. The run manifest records the consent in a new optional block, `consent: { irreversible: true, by: ... }`; a sub-playbook inherits its parent's consent (`inherited_from`) and a resume keeps it, because the manifest is write-once. Connector functions flagged `irreversible: true` still feed only V73, not this gate.

`docs/GUARDRAILS.md`, `docs/MCP.md`, `docs/CI.md`, `docs/HOWTO-authoring.md` and `docs/HOST-INTEGRATION.md` describe what is enforced where. The repository's own `apb-task-implement` 1.17.0 declares `effects: [irreversible]` on the nodes that push the feature branch, open the pull request, push review fixes and delete the merged branch, so a run of it now asks for the person's consent at start. `branch-quality-review` and `apb-task-brainstorm` push nothing and keep their effects.

## apb eval

A playbook can carry an eval suite under `.apb/playbooks/<id>/evals/`: one YAML case per file, with a fixture (a directory under `evals/fixtures/` or a ref of the repository), an optional change committed on a branch, an instruction, and checks over the finished run: its outcome, the playbook's own goal criteria, the visited route, node outputs, files in the tree, journal events, deliverables, and case scripts under `evals/scripts/`. No check asks a model. `apb eval <id>` runs every selected case, `--repeat` times, as an ordinary `apb run --detach --no-cache --execution cli` in a fresh repository under `<config-dir>/evals/scratch/`, whose only remote is a local bare repository; it stops a repetition that waits for a person or crosses its time, token or cost limit, and an invocation budget keeps the next repetition from starting once the reported spend reaches it.

Each result is stored in `<config-dir>/evals/<playbook>/<key>.json` under a key made of the playbook digest, the profile bundle digests, the resolved executors and the overrides, with the pass count per case, its Wilson interval, and the median cost and duration. Every invocation ends with a comparison against the previous stored result, naming the configuration change and the per-case delta; `apb eval <id> --compare` prints it without running anything. `--model`, `--profile-override` and `--overrides` evaluate another configuration, `--draft` a draft playbook (only the scratch copy is marked active), `--dry-run` prints the plan. The run directories move to `<config-dir>/evals/runs/`, so eval runs never appear in the project's runs, in `apb stats` or in `apb decisions report`.

Evals are opt-in and paid: every repetition is a full agent run, and nothing starts one except an explicit `apb eval`. An eval run is not a sandbox: the agent keeps the network and every CLI the operator is logged in to, so apb never evaluates a playbook with `irreversible` effects, a shipping step, a connector or a sub-playbook (V81), and a case's `env` can cut the known logged-in CLIs. The plan also names every node whose profile declares `environment: full`, because such a node loads the operator's own user-scope hooks, plugins and MCP servers in its eval runs. Case scripts are code outside every version digest: the suite runs from a copy whose digest must be approved on the machine (`--yes`, or yes on a terminal), and the approvals live in `<config-dir>/evals/approved.json`, apart from the trust store. New validation codes: V80 (a case does not parse, uses a field of a later release or names what the version does not have), V81 (the playbook cannot be evaluated), V82 (a gate or interactive node, where the run is stopped) and V83 (no case applies to the version).

The repository's own `branch-quality-review` carries the first two cases: `review-planted-defect` (the report must name an off-by-one loop planted in a twenty-line crate) and `review-clean-branch` (the same function written correctly; no finding above the lowest severity). `docs/EVALS.md` documents the format, the checks, the storage and the JSON output; `docs/HOWTO-authoring.md` has a short section on writing cases. Not in this release: mock connectors, scripted gate and question answers, push checks, an MCP tool and a dashboard card.

## apb runs shows the execution mode

`apb runs <run>` prints an execution line: `execution: cli` for a run without an execution block, otherwise the manifest's mode with its source, client and whether the host fallback is allowed (for example `execution: host (argument, client <name>)`), followed by `host fallback: <nodes>` for the steps the journal records as `execution_fallback`. `apb runs <run> --json` prints the same object as the MCP `run_status`, for a script that parses it. The `apb runs` table gets a mode column only when some run in it has an execution block, so a list of ordinary runs prints as before.

## Also fixed

- `supervisor_wait_keeps_the_heartbeat_fresh_while_it_blocks` failed once on a loaded CI runner. It now passes as soon as a heartbeat newer than the entry beat lands while the wait is still blocking, and the wait loop sleeps until the next beat when that comes before the next poll, so a cadence shorter than the poll interval is kept rather than rounded up. Production timing is unchanged.

## Upgrading

- **Irreversible playbooks need a consent at start.** This is a behaviour change for every start without a person at a terminal. A headless or CI `apb run` of a playbook whose tree declares `irreversible` is refused (`irreversible_requires_confirmation`) until the step adds `--confirm-irreversible`. A dashboard run of such a playbook now asks in the Run dialog, and a client that posts to the dashboard API without the dialog's `confirm_irreversible` is refused. An MCP host has to pass `acknowledge_untrusted: true` after asking the person, even for a trusted playbook. A playbook tree without `irreversible` starts exactly as before.
- **Trust.** The repository's own `apb-task-implement` 1.17.0 is a new version, so its trust has to be granted again before it runs, and each run now needs the consent above.
- **The manifest's `consent` block is optional.** Runs written by 0.24.0 of an irreversible playbook carry `consent: { irreversible: true, by: ... }` in their manifest; other runs have no such block, and a manifest without it reads as before. An older binary ignores the block, so it can resume such a run without asking, as it always did.
- **Eval suites.** `evals/` directories next to a playbook's versions are new; the registry never lists them as versions and editing a case never changes a version's trust digest. `apb validate` reports V80-V83 for them. `apb eval` writes only under `<config-dir>/evals/` (results, run directories, the scratch repositories while it runs, and `approved.json`); back it up with the rest of the config directory if you keep the results.

## Consent details

These points refine "Irreversible effects need a consent at run start" and "Upgrading" above, and win where they differ. MCP consent is its own argument: `playbook_run`, `playbook_execute_plan` and `run_resume` take `confirm_irreversible`, and `acknowledge_untrusted` answers trust only; for this release `acknowledge_untrusted: true` alone is still accepted as the consent, and the response carries a `deprecation` note. A trust refusal of an irreversible playbook also lists its `irreversible` sources, so the host asks one question that covers both. Every refusal carries a `consent_nonce` (a hash of the trust digest and the sorted sources); MCP `confirm_irreversible`, the dashboard's `confirm_irreversible` and `--confirm-irreversible=<consent_nonce>` accept that nonce, a nonce for another version of the tree is refused again, and a bare `true` (or a bare flag) still works for this release with a deprecation note. The dashboard dialog lists the refusal's structured sources and confirms with its nonce. `apb run` at a terminal prints the sources and asks `[y/N]` on the terminal instead of taking the terminal itself as consent, and never takes it inside a run (`APB_RUN_ID` set). `playbook_execute_plan` records `by: mcp:<client>`. Connector functions flagged `irreversible: true` that a node is granted count as consent sources, and a sub-playbook that does not resolve at an ungated start counts as needing consent. A supervisor patch may not add irreversible steps the run's consent does not cover (`patch_rejected`, `irreversible_requires_confirmation`); the manifest records the covered `sources`. Older runs of irreversible playbooks ask once on resume (`apb resume`, MCP `run_resume`), and the consent is then written into their manifest; a manifest consent is honoured on resume only for a run directory apb created on this machine. `playbook_trial` refuses a tree that needs consent, a sub-playbook included. New warning V90: a step that looks like a merge, push, deploy or publish by its name but declares no `irreversible` effect. The dashboard API trusts its authenticated caller: any holder of the dashboard token can send `confirm_irreversible`. `run_status` (and `apb runs <run> --json`) carries `execution.fell_back`, the nodes the text line names after `host fallback:`. The repository's `branch-reviewer` profile runs with `environment: minimal`.

## Eval details

Before release the eval runner was hardened against repository content it cannot trust, and `docs/EVALS.md` describes each point. Results live in `<config-dir>/evals/results/<playbook>/<key>.json` (not `<config-dir>/evals/<playbook>/`), are written under a lock, and a key file that does not parse is moved aside to `<key>.json.corrupt-<ms>` instead of being overwritten; comparisons use results of the same project only, and an invocation in which no repetition started is reported but not stored. A suite that cannot be digested (a symlink, a special file, over the suite limits of 50,000 files or 1 GiB) is refused and never approved, and a fixture is refused when a symlink leaves the scratch tree, sits at or below `.apb`, or when it carries `.git`; the definitions and the change overlay are copied without writing through links. Every git call apb makes in a scratch tree is hardened (the operator's `GIT_DIR` and friends removed, no hooks or filesystem monitor, the local transport only), the scratch repository clears `credential.helper`, and case scripts get the same git settings through `GIT_CONFIG_PARAMETERS`. The case `env` is applied only to the agents and scripts a run spawns, never to apb itself, and V80 refuses keys that reconfigure apb, the shell, the loader or git (`APB_*`, `HOME`, `XDG_*`, `PATH`, `LD_*`, `GIT_DIR`, `GIT_CONFIG*` and similar); the suite approval covers the env as well as the scripts. The wall-clock limit is also enforced by the run's own driver; SIGINT or SIGTERM stops the live repetition and cleans up (exit 130); a tree whose driver does not exit is moved to `<config-dir>/evals/kept/<eval-id>/<case>-<n>/` rather than deleted; stale scratch directories are swept at the next start. The invocation budget counts only reported cost, and `apb eval` warns when an executor reports none. V80 also names unknown event types in `events` checks, an explicit `goal: required` on a version without script or marker criteria, and skips node and param checks for cases whose `versions` exclude the loaded version. `--json` output carries `full_environment_nodes`, the not-a-sandbox note, `warnings` and `journal_agent_writable`. The `review-clean-branch` negative control no longer fails a clean report with a heading such as `## High-level summary`, and both repository cases record the goal (`goal: report`) since the playbook declares no goal criteria yet.
