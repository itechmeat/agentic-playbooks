# apb 0.24.0

A minor release. The `irreversible` effect is now enforced instead of only listed: a run whose playbook tree declares it starts only with an explicit consent, which the run manifest records. `apb eval` runs a playbook's eval cases in disposable repositories, stores the pass counts per configuration and compares them with the previous result. `apb runs <run>` shows the run's execution mode and prints the MCP `run_status` object with `--json`. The playbook schema stays at 2: every new field is optional, and an unconfigured run of a playbook without `irreversible` effects validates, runs and journals exactly as in 0.23.0. The changes that need attention are under "Upgrading". (#180)

## Irreversible effects need a consent at run start

Until now `effects: [irreversible]` was shown on the consent screens and read by V73, but nothing stopped a run that declared it. A run whose tree needs consent now starts only with an explicit one. The consent sources are the `irreversible` effects of the playbook, its nodes and every sub-playbook, recursively; the connector functions flagged `irreversible: true` that a node is granted; and a sub-playbook that does not resolve at an ungated start, which counts as needing consent. The engine checks it while it prepares the run, before anything is written, so no launch surface can skip it; the run gate returns the same refusal earlier as structured JSON: `irreversible_requires_confirmation`, naming the sources and carrying a `consent_nonce`, a hash of the tree's trust digests (the playbook's and every pinned sub-playbook's) and the sorted sources. A nonce given for another version of the tree, a changed sub-playbook included, is refused again. A trust refusal of an irreversible playbook also lists its sources, so a host asks one question that covers both.

Who consents: an MCP host that passes the new `confirm_irreversible` argument on `playbook_run`, `playbook_execute_plan` or `run_resume` after asking the person, with the refusal's `consent_nonce` (`by: mcp`, or `mcp:<client>` when the host names its client); `acknowledge_untrusted` answers trust only. A person at an interactive terminal who answers `y` to the `[y/N]` question `apb run` asks after printing the sources (`cli`); the answer is read from the terminal, and the question is never asked when stdin or stderr is not a terminal or inside a run (`APB_RUN_ID` set), because a process that merely inherited a terminal is not a person. A script author writing `--confirm-irreversible=<consent_nonce>` on `apb run` or `apb resume` (`cli_flag`), which is the consent of a CI step. A person confirming the dashboard's Run dialog (`dashboard`), which lists the refusal's sources and confirms with its nonce. A trigger, an event bridge posting to the dashboard API, or a headless start without one of these is refused. For this release a bare `true` (MCP and dashboard `confirm_irreversible`), a bare `--confirm-irreversible`, and MCP `acknowledge_untrusted: true` alone are still accepted as the consent, with a `deprecation` note in the response or a warning on stderr. The dashboard API trusts its authenticated caller: any holder of the dashboard token can send `confirm_irreversible`.

The run manifest records the consent in a new optional block, `consent: { irreversible: true, by: ..., sources: [...] }`, where `sources` is what the consent covered. A sub-playbook inherits its parent's consent (`inherited_from`) only for a node that consent covered. The consent is checked again where a run can grow or restart: a supervisor patch may not add a source the run's consent does not cover, nor point a consented sub-playbook node at another playbook (`patch_rejected` with `irreversible_requires_confirmation`); the engine refuses to resume an irreversible run whose manifest records no covering consent, whatever starts the resume; and the resume surfaces honour a manifest consent only for a run directory apb created on this machine. An older run of an irreversible playbook asks once on resume (`apb resume`, MCP `run_resume`), and the consent is then written into its manifest. `playbook_trial` refuses a tree that needs consent, a sub-playbook or a connector function included (`trial_forbidden_irreversible`). V73 still reads connector functions flagged `irreversible: true` as before. New warning V90 names a step that looks like a merge, push, deploy or publish by its id, title or script path but declares no `irreversible` effect, so the author declares it and a run asks; the name heuristic stays a hint, never a consent source.

`docs/GUARDRAILS.md`, `docs/MCP.md`, `docs/CI.md`, `docs/HOWTO-authoring.md` and `docs/HOST-INTEGRATION.md` describe what is enforced where. The repository's own `apb-task-implement` 1.17.0 declares `effects: [irreversible]` on the nodes that push the feature branch, open the pull request, push review fixes and delete the merged branch, so a run of it now asks for the person's consent at start. `branch-quality-review` and `apb-task-brainstorm` push nothing and keep their effects.

## apb eval

A playbook can carry an eval suite under `.apb/playbooks/<id>/evals/`: one YAML case per file, with a fixture (a directory under `evals/fixtures/` or a ref of the repository), an optional change committed on a branch, an instruction, and checks over the finished run: its outcome, the playbook's own goal criteria, the visited route, node outputs, files in the tree, journal events, deliverables, and case scripts under `evals/scripts/`. No check asks a model. `apb eval <id>` runs every selected case, `--repeat` times, as an ordinary `apb run --detach --no-cache --execution cli` in a fresh repository under `<config-dir>/evals/scratch/`, whose only remote is a local bare repository. It stops a repetition that waits for a person or crosses its time, token or cost limit; the engine also enforces the wall-clock limit inside the run's own driver, so the run stops even when `apb eval` is gone. An invocation budget keeps the next repetition from starting once the reported spend reaches it; it counts only reported cost, and `apb eval` warns when an executor reports none. SIGINT or SIGTERM stops the live repetition and cleans up (exit 130). A tree whose driver does not exit, or whose run directory sits behind a symlink the agent planted, is moved to `<config-dir>/evals/kept/<eval-id>/<case>-<n>/` rather than deleted; when even that move fails it stays in the scratch directory, which is then not removed, and the result names it with a warning. Stale scratch directories are swept at the next start.

Each result is stored in `<config-dir>/evals/results/<playbook>/<key>.json`, written under a lock, under a key made of the playbook digest, the profile bundle digests, the resolved executors and the overrides, with the pass count per case, its Wilson interval, and the median cost and duration. A key file that does not parse is moved aside to `<key>.json.corrupt-<ms>` instead of being overwritten, and an invocation in which no repetition started is reported but not stored. Every stored invocation ends with a comparison against the previous stored result of the same project, naming the configuration change and the per-case delta; `apb eval <id> --compare` prints it without running anything. `--model`, `--profile-override` and `--overrides` evaluate another configuration, `--draft` a draft playbook (only the scratch copy is marked active), `--dry-run` prints the plan. `--json` output carries `full_environment_nodes`, the not-a-sandbox note, `warnings` and `journal_agent_writable`. The run directories move to `<config-dir>/evals/runs/`, so eval runs never appear in the project's runs, in `apb stats` or in `apb decisions report`.

Evals are opt-in and paid: every repetition is a full agent run, and nothing starts one except an explicit `apb eval`. An eval run is not a sandbox: the agent keeps the network and every CLI the operator is logged in to, so apb never evaluates a playbook with `irreversible` effects, a shipping step, a connector or a sub-playbook (V81), and a case's `env` can cut the known logged-in CLIs. The case `env` is applied only to the agents and scripts a run spawns, never to apb itself. The plan also names every node whose profile declares `environment: full`, because such a node loads the operator's own user-scope hooks, plugins and MCP servers in its eval runs.

The runner treats repository content as untrusted. Case scripts are code outside every version digest: the suite runs from a copy whose digest, covering the scripts and the case `env`, must be approved on the machine (`--yes`, or yes on a terminal), and the approvals live in `<config-dir>/evals/approved.json`, apart from the trust store. A suite that cannot be digested (a symlink, a special file, over the suite limits of 50,000 files or 1 GiB) is refused and never approved. A fixture is refused when a symlink leaves the scratch tree or sits at or below `.apb`, or when it carries `.git`; the definitions and the change overlay are copied without writing through links. Every git call apb makes in a scratch tree is hardened (the operator's `GIT_DIR` and related variables removed, no hooks or filesystem monitor, the local transport only), the scratch repository clears `credential.helper`, and case scripts get the same git settings through `GIT_CONFIG_PARAMETERS`.

New validation codes: V80 (a case does not parse, uses a field of a later release, names what the version does not have, sets an `env` key that reconfigures apb, the shell, the loader or git such as `APB_*`, `HOME`, `XDG_*`, `PATH`, `LD_*`, `GIT_DIR` or `GIT_CONFIG*`, names an unknown event type in an `events` check, or sets `goal: required` on a version without script or marker criteria; node and param checks are skipped for a case whose `versions` exclude the loaded version), V81 (the playbook cannot be evaluated), V82 (a gate or interactive node, where the run is stopped) and V83 (no case applies to the version).

The repository's own `branch-quality-review` carries the first two cases: `review-planted-defect` (the report must name an off-by-one loop planted in a twenty-line crate) and `review-clean-branch` (the same function written correctly; no finding above the lowest severity, where a heading such as `## High-level summary` is not a finding). Both record the goal as `goal: report`, since the playbook declares no goal criteria yet. `docs/EVALS.md` documents the format, the checks, the storage, the hardening and the JSON output; `docs/HOWTO-authoring.md` has a short section on writing cases. Not in this release: mock connectors, scripted gate and question answers, push checks, an MCP tool and a dashboard card.

## apb runs shows the execution mode

`apb runs <run>` prints an execution line: `execution: cli` for a run without an execution block, otherwise the manifest's mode with its source, client and whether the host fallback is allowed (for example `execution: host (argument, client <name>)`), followed by `host fallback: <nodes>` for the steps the journal records as `execution_fallback`. `apb runs <run> --json` prints the same object as the MCP `run_status`, for a script that parses it; both carry `execution.fell_back`, the nodes the text line names after `host fallback:`. The `apb runs` table gets a mode column only when some run in it has an execution block, so a list of ordinary runs prints as before.

## Also changed and fixed

- The repository's `branch-reviewer` profile runs with `environment: minimal`: it lists no skills and its review tools are command-line tools, so the operator's personal setup only added hooks and context to every review.
- `supervisor_wait_event` keeps a heartbeat cadence of at least a quarter of its poll interval, so a zero or tiny cadence no longer reads the journal and writes the heartbeat every millisecond.
- `supervisor_wait_keeps_the_heartbeat_fresh_while_it_blocks` failed once on a loaded CI runner. It now passes as soon as a heartbeat newer than the entry beat lands while the wait is still blocking, and the wait loop sleeps until the next beat when that comes before the next poll, so a cadence shorter than the poll interval is kept rather than rounded up. Production timing is unchanged.

## Upgrading

- **Irreversible playbooks need a consent at start.** This is a behaviour change for every start without a person at a terminal. A headless or CI `apb run` of a playbook whose tree declares `irreversible` is refused (`irreversible_requires_confirmation`) until the step adds `--confirm-irreversible=<consent_nonce>` with the nonce the refusal printed; the nonce changes when the tree's trust digest or sources change. A dashboard run of such a playbook now asks in the Run dialog, and a client that posts to the dashboard API without the dialog's `confirm_irreversible` is refused. An MCP host has to pass `confirm_irreversible` with the refusal's `consent_nonce` after asking the person, even for a trusted playbook. The bare forms (`--confirm-irreversible`, `true`, and `acknowledge_untrusted: true` alone) still work in this release with a deprecation note and will be removed later. A playbook tree without `irreversible` starts exactly as before.
- **Trust.** The repository's own `apb-task-implement` 1.17.0 is a new version, so its trust has to be granted again before it runs, and each run now needs the consent above.
- **The manifest's `consent` block is optional.** Runs written by 0.24.0 of an irreversible playbook carry `consent: { irreversible: true, by: ..., sources: [...] }` in their manifest; other runs have no such block, and a manifest without it reads as before. A run of an irreversible playbook started before 0.24.0 asks for the consent once when it is resumed. An older binary ignores the block, so it can resume such a run without asking, as it always did.
- **Eval suites.** `evals/` directories next to a playbook's versions are new; the registry never lists them as versions and editing a case never changes a version's trust digest. `apb validate` reports V80-V83 for them. `apb eval` writes only under `<config-dir>/evals/` (`results/` with a `store.lock` per playbook, run directories under `runs/`, the scratch repositories while it runs, trees kept under `kept/`, and `approved.json`); back it up with the rest of the config directory if you keep the results.
