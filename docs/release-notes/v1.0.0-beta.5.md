# apb 1.0.0-beta.5

The fifth beta of apb 1.0 makes the decisions only a person may take hold
against a coding agent that runs as the same user: a person-only gate or an
approval is decided with a passkey, and a run that carries such gates can no
longer be resumed by an older apb past them.

## Installing the beta

1.0.0-beta.5 is published as a GitHub pre-release. The `latest` release and
the Homebrew formula stay on 0.25.0, and `apb self-update` of a stable
install stays on the stable line. A beta install from beta.4 on reaches this
one with `apb self-update`; an earlier beta uses the installer below.

Shell installer for this tag (macOS, Linux x86_64):

```sh
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/itechmeat/agentic-playbooks/releases/download/v1.0.0-beta.5/apb-installer.sh | sh
```

## Passkeys for person-only decisions

A channel refusal proves a caller type, not a person: whoever holds a
server key can sign in to the dashboard and decide. With at least one
passkey enrolled on the machine, apb raises the bar. A person-only gate's
decision, an approval (a gate with `approves` or `requires_approval`) and
a publish consent then need a fresh WebAuthn assertion made through the
dashboard, bound to the run, the gate, the request and the chosen option,
and the drive re-verifies the assertion against the store when it
consumes the decision. With no passkey enrolled, behavior is exactly as
before.

A passkey decides nothing on its own; it says the same person who
enrolled it was at the browser for this decision, on the three surfaces
the passkey gates: person-only gates, approvals and publish consents.
Ordinary review gates, judge decisions and questions are unchanged.

To enroll one, run `apb passkey enroll` at an interactive terminal. It
prints a one-time code, valid five minutes, and asks the person to type
it back; the code is stored only after that confirmation, and the
dashboard's Passkeys page then asks for it and runs the registration
ceremony. This needs a secure context, so the dashboard must be reached
at localhost or over HTTPS; a dashboard at an IP literal cannot use
passkeys at all, since a WebAuthn credential cannot bind to an IP
address. Every later passkey is added through the dashboard with an
assertion from an existing one. `apb passkey list` shows them, and
`apb passkey remove <label>` removes one; every removal, last passkey or
not, needs a one-time code typed back at the terminal, the same rule the
dashboard enforces with an assertion, under the store lock. Enrollment
and removal journal nothing into runs; each sends a notice to the
machine's notify target when one is set.

The store is `<config_dir>/passkeys.yaml`, one entry per passkey
(credential id, COSE public key, sign count, label, created time),
written 0600 and atomically. Nothing secret is stored and nothing secret
is logged; the authenticator's private key never leaves it.

With a passkey enforced, `apb review` and `apb publish approve` print the
dashboard link and refuse with `passkey_required`; MCP and a run step are
refused as before, and a bearer-key request is refused even when it
carries a valid assertion token, since a key-made client is never a
person. A hand-written line in the run's channel file, whatever fields it
forges, carries no assertion and is never consumed; on a person-only gate
nothing is exempt for the live drive, and the engine's own decisions are
exempt only where the journal and the manifest corroborate them. When the
store exists but does not read, nothing falls back: the requirement
stands and every person-only decision refuses until the file is fixed
(fail closed), and `apb doctor` reports it as a failure. A run step whose
isolation sandbox keeps `<config_dir>` out of reach can neither enroll
nor assert.

The boundary is apb's surfaces and the run files, not the config dir
against its own user. A process running as the same user can append a
record with its own key into `passkeys.yaml` and enroll it silently, and
it can delete the file, which reads as "no passkey enrolled" and switches
the whole requirement off silently; the only trace of a deletion is the
warning row `apb doctor` shows, which recommends enrolling again.
Nothing inside the same user id can be made tamper-proof against such a
writer, which could replace the `apb` binary and the dashboard assets
too. Details in `docs/GUARDRAILS.md` ("Passkeys on person-only gates and
approvals") and the passkeys spec
(`docs/superpowers/specs/2026-11-04-passkeys-design.md`).

## Older binaries refuse guarded runs

A run whose playbook has person-only gates or approvals records
`execution.mode: cli+guard` (or `host+guard`) in its manifest. Every apb
from 0.23 on refuses to resume such a run and says it was written by a
newer apb; it still reads and stops it. `apb runs`, `run_status` and the
run page show the base mode with a guard attribute. An apb older than 0.23
does not read the execution block, so every apb on a machine that runs
these playbooks must be this release or newer; `apb doctor` warns about
other `apb` binaries on `PATH`. A supervisor patch that adds a person-only
gate to a running run journals the guard but cannot rewrite the manifest,
so for that run the older stop-then-resume limit stays open.

## Fixes

- A run whose own `run.yaml` does not parse withholds its text as
  `[secrets_unresolved]` and names the config error, instead of printing
  text that might hold a declared secret. The runs list shows the row with
  the error and keeps the other runs readable.
- Review leftovers from #255 to #261 (#264): evidence sessions show while
  their attempt runs, an unknown project directory is marked as such, and
  smaller fixes in result capture, citations, run search, interventions,
  stats, the project registry, the report graph and the daily cleanup.

## Compatibility

- `execution.mode` in a new run's manifest may carry a `+guard` suffix;
  readers of this release report the base mode with `guarded: true`.
- The new passkey store `<config_dir>/passkeys.yaml` is read by every
  apb that decides a person-only gate and by `apb doctor`; older
  binaries ignore it. Enrollment and removal journal nothing into runs.
- A decision on a person-only gate, an approval or a publish consent can
  queue channel entries in the run's `reviews.jsonl` that carry the new
  `passkey` and `passkey_proof` fields; a reader of this release
  re-verifies the proof before it consumes the entry, and an entry
  without a verifying proof is never consumed.
- The closed `CallerRefusal` list gains `passkey_required`, so MCP tool
  errors and HTTP 403 answers can name it; readers that do not know the
  code see an unknown refusal.
- The dashboard server on loopback gains the passkey ceremony routes
  (`/api/passkeys`, `enroll/start`, `enroll/finish`, `assert/challenge`,
  `assert/verify`), used by the dashboard's Passkeys page only.
- Verification of the WebAuthn ceremonies adds the `ed25519-dalek`
  dependency (BSD-3-Clause), beside `p256` and `ciborium` (both MIT or
  Apache-2.0); no `webauthn-rs`, whose license is not compatible.
