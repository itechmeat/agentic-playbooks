# apb 0.24.2

A patch release. Host tasks now come with one execution contract: run them with your own subagents, never through another agent CLI. CI and the release workflow also run faster and with narrower tokens.

## Host tasks state how to run them

In host execution mode apb starts no agent CLI. The agent that started the run executes each host task with its own subagents. apb never said this to the host, and a task's `model_hint` read like an order to run the profile's model. So one host agent executed every task of a run by launching external `claude -p` processes with permission-bypass flags. That work fell outside the session's permissions and its usage accounting, and it brought back the external executor that host mode removes.

The engine now owns one execution contract for host tasks, worded in one place and shown verbatim wherever a task is handed to the host:

> Execute this task in the current session with your own subagent tool, or do it yourself. Do not launch another agent CLI or process to run it (such as claude -p, codex exec, opencode run, gemini or a ZCode CLI), and never with permission-bypass flags. The profile's executor agent and model do not apply in host mode, and model_hint is advisory only: choose among the models your own subagent tool offers, use your session's model when none matches, and report the model actually used as run_task_submit model (apb tasks submit --model).

Where it appears:

- The `next` instruction of `run_wait` when it returns `needs: host_task`. `supervisor_wait_event` now returns that `next` as well whenever tasks are pending.
- A new `execution_note` field on every pending task, in `run_wait`, `run_status`, `supervisor_wait_event` and `apb tasks --json`.
- The `run_wait` and `run_task_submit` tool descriptions.
- One `execution:` line at the top of `apb tasks` and `apb tasks --full`.
- The dashboard's host task panel.

Every `hint_note` now starts with `advisory:`, for example `advisory: model hint M (fallback 1 of 1 declared by profile P after attempt 1 failed; the host picks its own model)`. `docs/HOST-INTEGRATION.md` has a new section, "The execution contract", and `docs/MCP.md`, `docs/PROFILES.md` and `docs/HOWTO-authoring.md` point to it. Every change is additive or a wording change. No event or schema changed.

## Faster CI

- **The Linux job is split.** It now runs as three parallel jobs: `web`, `lint` (fmt, clippy, cargo deny) and `test-linux` (nextest, doctests). A `build-and-test` job over them keeps the required check name.
- **Twice the test workers.** The `ci` nextest profile now runs 8 workers. The suite mostly waits on processes and timers: on 4 cores it took 72 s with 4 workers and 40 s with 8.
- **Result.** CI wall time on a pull request fell from a median of 326 s to about 220 s.
- **Caches.** Cargo caches are saved only on main, and a run on main is never cancelled.
- **The required macOS check is now reliable.** `test-macos` is now required. It used to fail intermittently: the test HTTP stub replied before it had read a chunked request body, so the kernel reset the connection, and on macOS the client's next socket call failed with EINVAL. The stub now reads the whole body first. (#187)

## A faster release workflow

The release build legs used to run the whole test gate before building, so the Intel macOS leg spent about 1000 s on checks before its 916 s build. The build legs now only build. The gate runs beside them as a matrix: one Linux leg plus macOS arm and Intel legs. It remains the job that publishing requires, so a failing leg still blocks the release. CI, the gate and dist's global jobs now pin `ubuntu-26.04`. The gnu build stays on `ubuntu-22.04` for glibc compatibility. Workflow tokens are read-only except for the job that applies the release notes, and checkouts no longer keep credentials. (#187, #188)
