# apb 0.20.2

A patch release with one fix: a run start that arrives while the workdir is busy is queued instead of thrown away.

## A busy workdir no longer destroys the request that arrived during it

One project checkout has one write-run at a time. A run that writes to the workdir holds `.apb/workdir.lock` for its whole life, and `POST /api/playbooks/{id}/run` used to answer `429` to anything that arrived during one. For a human at the dashboard that is a fair answer: retry in a moment. For a machine it is not an answer at all. A webhook bridge that turns inbound messages into runs has nowhere to put a refusal, so the message it was carrying is destroyed the moment the POST fails, and the provider will not send it again. (#120)

That was not a corner case. Every write-run holds the lock, including short ones, so the window is open whenever the engine is doing anything at all: a customer's reply arriving while a sale is parked on a `wait` node, and equally a routine supplier event arriving while a thirty-second run absorbs the previous one.

The start is now admitted instead. The run directory, the playbook snapshot and the request's run parameters are written, the run id comes back `200` exactly as before, and the engine claims the workdir as soon as the holder releases it. Persisting the start IS the queue: there is no second event store to keep in sync with the runs, and nothing is held in a process's memory. (#120)

A queued run is journaled `run_queued` with the holder that blocked it, and reads as running rather than paused, because it is running as far as its caller is concerned. It simply has not reached its first node. The wait ends at the next journal entry either way: the first `node_started` when the lock is granted, or `run_error` plus `run_finished` when the queue wait runs out. An admitted event that never executed is still findable, with the reason attached.

`server.workdir_queue_wait_seconds` sets the ceiling, 900 seconds by default. `0` turns queueing off and restores the immediate `429` with its `Retry-After` hint, which is the right setting only where every caller is a human reading the answer. Nothing changes for the CLI or the MCP tools: a start that did not ask to be queued still fails fast on a busy workdir, before any run directory exists. (#120)
