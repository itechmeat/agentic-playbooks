# apb 0.24.4

A patch release. A fork can now stop at the first failure in any of its branches, a join can refuse to run when a branch arrived dead, and parallel branches no longer wait for each other step by step. apb also knows the Claude 5.5 models. (#195)

## Failing a fork early

A failed node inside one branch of a fork used to leave the other branches running. Its failure route usually led to a node that every branch feeds, an implicit join, so the run waited for every sibling before the failure was handled. In one field case a design failure let the content branch run about 15 more minutes.

The forking node now takes a policy:

```yaml
- id: split
  type: agent_task
  fork: { on_branch_failure: fail_fast, on_failure: rejected }
```

- `wait` (the default) keeps today's behaviour.
- `fail_fast` stops the fork at the first failed node in any branch, after its retries and fallbacks. Running siblings are interrupted, branch nodes that have not started are cancelled, the fork's join never runs, and the run goes to `on_failure`, which runs once.
- `cancel_siblings` cancels the same way, then follows the failed node's own failure route.

**What counts as a branch.** A node belongs to a branch when every path from the fork to it passes through that branch's first node, so rework loops and dead ends that only one branch reaches stay in their branch.

**Nested forks.** The innermost fork with a policy decides first. A failure that nothing inside it handles escalates to the enclosing fork.

**Host mode.** A cancelled branch's pending host task is closed with a note naming the fork, its policy and the failed node.

**Resume.** A resumed run keeps the decision: cancelled branches stay cancelled. A run whose driver died between the failure and the policy record gets the policy applied on resume.

Each decision is journaled as `branch_failed` and `branch_cancelled`. `run_status` lists them as `branch_failures`, and `apb runs <id>` and the dashboard event list show them.

## Joins that refuse dead branches

A branch that failed and took its failure edge arrives at a join as dead, and so does a branch that routed elsewhere. A dead arrival counts as satisfied, so the join ran as soon as the other branches arrived, as if nothing had failed. `docs/HOWTO-authoring.md` now spells this out.

`require: all_succeeded` on an incoming edge makes the join refuse instead:

- The join node does not run.
- `join_refused` is journaled.
- The join finishes failed and takes its failure route. Without one, the run fails with the refusal as its reason.

The validator checks the new options:

- **V77:** `fork` on a node that does not fork.
- **V78:** an `on_failure` that is missing under `fail_fast`, set under another policy, or points at the start node, the fork itself, a node inside its branches or one of its joins. Also `fail_fast` on a fork with a `join: any` join.
- **V79:** `require` on a node that is not a join, or together with `join: any`.

## Parallel branches run continuously

Ready branch nodes used to run in passes, and a pass ended only when every member ended. A short step in one branch therefore waited for a long step in another before its successor could start, and a failure late in a branch could not interrupt anything.

The drive now routes each branch node as it finishes. When one succeeds, its ready successors start right away, up to `max_parallel`, but only while another branch node is still running or queued. The node that finishes last hands its successors to the ordinary one-at-a-time path, so the chain after a join runs node by node as before. The control scan, the supervisor watch, context compaction and commit attribution all still run between those nodes.

**What still waits for the running branch nodes to end:**

- Successors that cannot run alongside others: human review, wait, condition, prompt and finish nodes, sub-playbooks, explicit `join:` barriers, `require` joins, and interactive and `protect` nodes.
- Loop re-entries, and a successor that leads back to a branch node that is still running.
- Everything after the node that publishes the run's working tree, so later nodes start inside that tree.
- Anything after a failure. Once a branch node fails, nothing new starts and the failure is handled when the running nodes end. A fork policy still interrupts them at once.

A branch node gets its commits recorded only when it ran alone, as before.

## Claude 5.5 models

- **New models.** `claude-sonnet-5-5` and `claude-haiku-5-5` join `claude-opus-5-5` and `claude-fable-5-1` in the curated models table, so `apb validate` and `apb doctor` no longer warn `model_unknown` for them. The older ids stay listed.
- **Newer models of a known family.** A Claude id that apb does not list yet but that is well formed for a known family (`claude-<family>-<major>-<minor>` or `claude-<family>-<major>`, with family `opus`, `sonnet`, `haiku` or `fable`) passes with an info note, `model_new_in_family`, instead of a warning. Unknown families and malformed ids still warn.

## Compatibility

- **New fields and events.** The new playbook fields and the new events are additive.
- **Resuming with an older apb.** A run that uses `fork` or `require` must be resumed by apb 0.24.4 or newer. An older apb ignores the new fields and events and would route such a run as if they were absent.
