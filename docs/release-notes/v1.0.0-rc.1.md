# apb 1.0.0-rc.1

The release candidate of apb 1.0. The feature work of the 1.0 plan is
complete; this release freezes what 1.x promises, states the platform
position for macOS, and starts the soak that decides whether rc.1 becomes
1.0.0. Unless the soak finds a defect, the next release is 1.0.0 with no
further changes.

## Installing the release candidate

1.0.0-rc.1 is published as a GitHub pre-release. The `latest` release and
the Homebrew formula stay on 0.25.0, and `apb self-update` of a stable
install stays on the stable line: a stable install does not see the
candidate. A beta install reaches it with `apb self-update`.

Shell installer for this tag (macOS, Linux x86_64):

```sh
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/itechmeat/agentic-playbooks/releases/download/v1.0.0-rc.1/apb-installer.sh | sh
```

With cargo (Rust 1.99 or newer and a C compiler and linker: the Xcode
Command Line Tools on macOS, `build-essential` on Debian or Ubuntu; no
bun, the dashboard is inside the package):

```sh
cargo install --locked agentic-playbooks --version 1.0.0-rc.1
```

`--locked` builds with the exact dependency versions the release was
tested with. The binary is `apb`.

## The compatibility freeze

`docs/COMPATIBILITY.md` states the 1.x promise and how it is guarded.
From this release on:

1. The playbook schema is frozen: a definition that parses and validates
   on 1.0 parses on every 1.x with the same error codes; a field may be
   added, never removed or renamed.
2. The run journal is frozen: every 1.0 event type and field keeps its
   name and shape, a new field is optional and adds no member at its
   default, and a new event type is safe to skip up to the next
   checkpoint.
3. The MCP tools are frozen: a tool and an argument keep their names,
   every input a 1.0 tool accepts stays accepted (bounds, integer widths
   and enumerated values only widen), no tool or argument object gains a
   required member, and a tool served read-only stays served.
4. Validator codes are frozen: a code keeps its meaning and its severity,
   a retired code keeps its number, and a line of the frozen list is
   never removed. V15, never emitted, is listed retired beside V16, so
   its number is never reused.
5. The machine names and files are frozen: the reason, refusal and guard
   codes keep their spelling, and a run's `manifest.yaml` and `run.yaml`,
   profile files, connector manifests and account files of both scopes,
   `policy.yaml`, `config.yaml`, `decisions.yaml`, start rule documents,
   the signed stores and the playbook store (versions, `current` with its
   history, the `candidate` pointer, the provenance sidecar, the trust
   store, the launch floors) written by 1.0 still read with the same
   meaning.
6. The result keys of every documented result variant of the tools a host
   is told to consume stay, with the result's envelope (a JSON payload or
   an error) and the machine code of each documented refusal.

The promise is guarded by frozen fixtures and tests for each area: the
schema corpus, the journal (one line per event type), the MCP tool
schemas and result keys, the validator code registry with an executed
witness per code, the machine codes and guard names, the run and settings
files, the signed stores and the playbook store. A failing freeze test is
a compatibility break to fix, never a fixture to regenerate.

## Install with cargo

1. apb installs with `cargo install --locked agentic-playbooks`
   (a pre-release with `--version`); it needs Rust 1.99 or newer and a C
   compiler and linker. The crate named `apb` on crates.io is an
   unrelated project: `cargo install apb` does not install this tool.
   The six `agentic-playbooks-*` library crates are internal to the
   `apb` command and not a public API.
2. `apb self-update` on a cargo install does not update it: it names the
   cargo command (`cargo install --locked agentic-playbooks`) and exits
   2. Update by running the same command again; uninstall with
   `cargo uninstall agentic-playbooks`. Remove one install before
   switching to another channel (`docs/INSTALL.md`).
3. Building from source writes the dashboard to
   `crates/apb-server/dashboard/` (before: `web/dist/`), and the
   development commands of the six libraries name their packages
   (`cargo test -p agentic-playbooks-core` instead of
   `cargo test -p apb-core`; `cargo test -p apb` stays). `cargo install
   --git` is not supported: a git checkout has no built dashboard.

## Platforms

Linux and macOS are supported; Windows is not. Isolation `full` needs
Linux with unprivileged bubblewrap. On macOS, `isolation: full` refuses
with `os_unsupported` and `best_effort` runs without a sandbox, for the
whole 1.x line: the refusal sentence shown by the fit report and
`apb doctor` states this position, so a playbook that needs the sandbox
is asked for on Linux from the start.

## Changes of the 1.0 plan since beta.7

The lines below are the user-visible changes of the thirteen earlier
changes of the 1.0 plan, none of which was in a released beta. They were
merged into main before this release; this is their first release.

### People in the loop

1. A review gate that uses `max_scope`, `fields` or `show` shows what the
   decision covers: commits, changed files and lines, list items settled,
   connector writes, sends and result snapshots, as counts only. `apb
   stats` and the run outcome report such decisions made faster than
   their scope takes to read. A plain gate and a publish consent journal
   their request as before, so an older apb still resumes a run waiting
   there.
2. A gate can withhold options above a size limit (`max_scope`); a
   withheld option is refused on every channel.
3. A gate can show earlier outputs (`show:`) and take typed values
   (`fields:`); a gate with fields outputs one JSON object instead of the
   bare decision word, and routing on `review_status` is unchanged. A
   passkey assertion covers the values. An older apb refuses to continue
   such a run.
4. Every new version directory carries `playbook.mmd`, a flowchart text
   derived from the definition; `apb diagram` prints it, MCP
   `playbook_get`, the dashboard playbook page and the HTML report show
   it, and `apb doctor` names missing, stale and edited diagrams. The
   file is derived: an edit of it is overwritten at the next version
   write, move of `current` or `apb diagram --rebuild`.
5. A decision on a gate that uses a form feature names the request it
   answers (`apb review --request review:<seq>`, the `request` argument
   of MCP `review_decide` and of the HTTP route). One that names none, or
   names a request the gate asked again since, is refused `decide_again`;
   before, it could answer the newer request.

### Before running alone

1. A list node with `pilot:` runs its first items, then stops at a gate
   on the list node (`continue`, `revise` with a note, `stop`); a list
   with `stop_when:` may end early, failed, with items left pending
   (counted after the pilot, never inside it). An unattended run fails at
   a pilot gate unless the pilot declares `unattended: continue` and
   every slice item passed.
2. `policy.yaml` accepts `unattended:`; an older apb reads a file with it
   as invalid.
3. The fit report (`apb adopt`, MCP `playbook_adopt_report`, the
   dashboard fit card) says whether a playbook is ready to run alone:
   done defined by an enforced script goal criterion, every acting agent
   step checked by a script, every acting node bounded in its working
   tree and at each connector it binds and on the network, a budget,
   every irreversible step behind a gate a decision model cannot decide,
   and its probation, counted in attended runs. `apb run --unattended`
   warns when it is not; with `--require-ready` the start is refused when
   the loaded version or a sub-playbook it starts is not ready.
4. A playbook with `unattended: { after_attended_successes: N }` (or a
   `policy.yaml` asking the same) refuses unattended starts until N
   attended successful runs of its exact definition ended in the same
   project on this machine. They are counted from a signed probation
   ledger per playbook and project (`.apb/probation/`), written from this
   release on. `apb run --waive-probation` (it asks for the playbook id
   typed at an interactive terminal) or `unattended.waive_probation` in
   the machine `policy.yaml` waives it. A supervisor's patch of an
   unattended run is refused unless the patched version passes the same
   checks. An apb older than this release ignores the `unattended:` block
   and starts such a playbook unattended without probation: keep every
   apb on such a machine at this release or newer (`apb doctor` warns
   about others on `PATH`).

### Typed inbox reads

1. `inbox_read` accepts `types` and `where`; a filtered read
   acknowledges the events it skips for its own consumer only, and only
   for a caller granted the ack function too (a read-only grant, an
   engine check and a read-only process move no cursor), reports
   `skipped` and never hides a gap.
2. A connector's `webhook:` block may name the event type
   (`event_type_header` or `event_type_path`).
3. The bundled github connector 0.4.0 receives signed webhooks typed by
   `X-GitHub-Event` and offers `inbox_read`, `inbox_ack` and
   `inbox_peek_depth`; whatsapp 0.2.0 types its deliveries.

### Wait park

1. A timer wait with more than a minute left pauses the run until the
   timer is due: no driver and no agent runs, the tree of a write run
   stays locked, and the run resumes itself when the timer is due, also
   after a reboot through `apb resume --all`. It reads `paused` with the
   line "waiting on timer `<node>` until <time>", and no "paused"
   notification is sent for it. A timer wait that pauses this way is not
   counted as an intervention in `apb stats` or the retro; a person's
   resume of it is.
2. A run whose playbook has a timer wait carries the run guard
   `wait_park`: while such a run waits on its timer, an apb older than
   this release refuses to resume or pause it, and can still read and
   stop it. Once an older apb stopped such a run, resuming it with that
   older apb counts the time it waited as paused, so the timer waits
   again and a run deadline may end the run.
3. Two control commands sent to the same run at the same moment (for
   example a pause and a supervisor note) are both applied; before, they
   could take the same number and one of them could be skipped.
4. Reminders for an open wait: a run can remind a person on a cadence
   (`notify.remind` in `policy.yaml`, the machine's list; a project only
   turns it off) while its review, question or host task stays open.

### Eval doubles

1. `apb eval` evaluates playbooks that act through connectors: an eval
   case's `connectors:` answers every call from recorded answers, never
   the service, and `checks.connector_calls` asserts the input arguments
   of the dispatched calls, before the connector's text modes and send
   markers. The accounts' variables must still be present; no value is
   sent, and one is read only to scrub the captured arguments.
2. A case of a connector playbook without full doubles is refused
   `invalid_suite` (V81 or V280) where 0.24 refused it
   `eval_refused_effects`; both before anything runs.
3. `completion_check` labels in `apb decisions report` read only a
   person's approval of the reply, recorded through a person's channel;
   the report suggests no `completion_check` threshold, and earlier
   stored `completion_check` thresholds no longer enforce.
4. Run guards: a doubled eval run carries `eval_doubles`; an older apb
   that knows run guards refuses to resume or pause a run whose journal
   holds it.
5. Captured eval call arguments are stored only when every secret the
   workspace's connectors reference can be scrubbed; otherwise they are
   withheld and an assertion over them is indeterminate.

### Secret params in run files

1. A secret param is never rendered: a playbook that references a param
   declared `secret: true` in any template is refused with V340, at
   validate, at save and at run start. A run started before this release
   that does so is refused at resume (`secret_param_rendered`); stop it
   and start it again.
2. A param declared secret stays secret for the run: a supervisor's patch
   that removes `secret: true` or removes the param while it is still
   referenced is refused (`secret_declaration_dropped`), and a waiting
   candidate that renders a secret is skipped and the start runs
   `current`.
3. A script reads a param from `$APB_RUN_DIR/run.yaml` under the
   top-level `params` key, which holds the run's resolved values; the
   file is YAML, mode 0600.

### MCP tool connectors

1. Connectors can map the tools of an MCP server over stdio: `mcp:` in
   `connector.yaml`, one server process per call. An older apb cannot
   load a connector manifest with an `mcp:` block: it refuses to start
   such a run, and in a run it resumes, each call of an mcp function
   fails before anything starts.
2. `apb connector approve <c> --account <a>` pins an MCP connector's
   program (its path and file digest) and tools under the connector's
   tree and account digests; it is a person's act in two confirmations,
   at an interactive terminal only. Neither a script, a run step, MCP nor
   the dashboard approves an MCP connector. A call whose definition,
   program or tool changed is refused until the account is approved
   again. The approval says once that the program runs as you,
   unsandboxed, and warns when the command is an interpreter or a
   launcher.
3. A run start with unpinned MCP tools is refused `mcp_tools_unpinned`,
   with a manual next action.
4. A new call outcome `tool_error`: an MCP tool reported an error, asked
   for input or started a task, or the server answered with a JSON-RPC
   server error, and whether it acted is unknown.
5. The program that runs is the file that was hashed (on Linux it starts
   from the hashed descriptor; elsewhere its path is hashed again right
   before the start). The server runs in a fresh private working
   directory, leads its own process group, and the close ends that group.
   A definition cannot set a variable that changes what code the server
   loads (`mcp_env_loads_code`).

### One point oh fixes

1. GitLab connector 0.3.0: `create_release` carries a hidden marker in
   its description. A retry after a lost answer is recognized as already
   sent (looked up with the new `list_releases`), and an outcome that
   cannot be settled is a send a person resolves (`apb intent resolve`).
2. Baseline: `project_checks.junit` reads failing tests from the JUnit
   XML reports a `test` command writes (V320), in a run that holds its
   working tree; a run that shares it reads them unknown. An older apb
   refuses a definition that sets it.
3. Fixes: hermes's resume form is a valid command line; `apb doctor`
   names a playbook directory a stopped copy or draft creation left; the
   dashboard profile editor sets `process_env`.
4. Connectors: `apb connector approve` is refused inside a run step, and
   the dashboard approves a connector or an account only through a
   signed-in session.

### MCP over HTTP and the surfaces

1. MCP connectors can reach a server over Streamable HTTP (`transport:
   http`, the 2026-07-28 revision) with a header token or the existing
   `oauth2_refresh` account; the endpoint is https only (plaintext is
   refused, on the loopback too), is approved with the account, and is
   checked before any secret is resolved; a person approves it at an
   interactive terminal, as a stdio server. Neither the transport nor its
   token request uses the calling process's proxy variables.
2. `apb connector tools <c> [--account <a>]` shows an approved MCP
   server's tools with their status and exits 3 when any changed.
3. `apb connector doctor`, MCP `connectors_list` and the dashboard's
   connector page show an MCP connector's approvals without starting its
   server.
4. New validator error V303: an http MCP connector's auth header may not
   name a header the transport sets. Over HTTP a server whose tools carry
   `x-mcp-header` annotations is refused.

### Incremental lists and session fork

1. A list node can skip items that passed in the previous successful run
   (`list.skip`). Any new playbook version, changed param or
   instruction, changed profile, connector account or decision setting,
   changed script or working tree makes every item run again once; the
   fields you name in `unless_changed` decide when an item itself counts
   as changed. Skipped items count as passed and are shown as skipped.
2. `continue_session: { from, mode: fork }` starts from a copy of another
   node's session; forks of one session may run at once (claude and
   opencode; other agents start cold with the reason).

### Start rules

1. Start rules: `apb trigger` (`set`, `list`, `show`, `approve`,
   `enable`, `disable`, `remove`, `log`, `test`), the dashboard's
   Triggers page, MCP `trigger_list` and `trigger_test`; nothing starts
   without a rule a person wrote and approved.
2. A rule is changed and approved only by a person: at a terminal with
   its name typed, or in a signed-in dashboard. Every rule needs an
   approval to start anything; any change of the rule drops it, and a
   start attempted under a changed approval binding revokes it. A rule is
   saved only in a registered project.
3. Each matching event starts its run at once or is recorded with its
   reason; the rule's key is the start key, so one key starts one run
   while it lives. Runs at once are the playbook's `concurrency:` block;
   a rule caps starts per hour.
4. A rule's run is always unattended and keeps its driver on a long wait.
   The sweep runs in the ingest listener (`apb ingest`, or `apb
   dashboard` with `ingest.enabled`) and once in `apb resume --all`; it
   never runs inside a run step, and `apb doctor` warns when enabled
   rules exist and no sweep runs.
5. A rule's run names its rule (`triggered_by`) on `apb runs <id>`, MCP
   `run_status`, the dashboard and the HTML report. Time-based starts are
   not in this release: an outside timer calling `apb run --start-key` is
   the way.

### Inbox waits

1. `wait_for: { type: inbox }` waits for the first matching event in a
   connector account's inbox and hands the next node the values of the
   fields the playbook declares. It keeps its place in its own run's
   journal, stores no event body and acknowledges nothing. A long inbox
   wait parks like a long timer wait, and a stored event resumes it
   within the waker's poll.
2. A playbook with an inbox wait carries the run guard `wait_park`; an
   older apb cannot load such a definition at all.
3. An inbox event counts only when it was stored before the wait's
   timeout on the run's paused-interval clock, however late the run reads
   it.
4. A parked wait reads "waiting at `<node>` until <T> at the latest" on
   every surface (was "waiting on timer"). Eval cases refuse a playbook
   with an inbox wait.

### Templates and global playbooks

1. Templates: `apb templates list | show | install <id> [--scope
   project|global] [--as <id>]` and the dashboard Templates page install
   an example playbook as a draft (apb approves nothing for it) with its
   eval scenarios and say what it still needs.
2. Global playbooks: `apb run <id> --scope global` starts a global
   playbook in the current project (also `--detach` and host execution;
   `--supervise` is refused for it); the dashboard lists global playbooks
   and shows one with its fit for a chosen project and the commands that
   run it (starting and editing stay on the CLI).
3. HTTP: the playbook list entries and the playbook detail carry `scope`;
   the detail takes `scope=project|global`.
4. A run of a global playbook no longer touches a project playbook of the
   same id: grading it does not re-decide the project's candidate, the
   project's quality comparison does not count it, and a supervisor patch
   of it is refused `patch_global_unsupported`.

## The soak

The candidate becomes 1.0.0 when the soak below is complete and clean.
The soak results are reviewed by release-1.0.0.

1. At least 14 days on rc.1.
2. Three code routines and three non-code routines run on rc.1: one of
   each started by a start rule, one with a human gate, one with an MCP
   tool connector.
3. No open defect of severity "wrong result, lost or repeated send, or
   security".
4. Ten consecutive green CI runs on main, every leg, no rerun.
5. On a macOS desktop session, one publish step whose remote needs the
   keychain credential helper: no dialog appears, or the push times out
   within its bound. The result is written into the limit
   `docs/PUBLISH.md` states (it says `GCM_INTERACTIVE=never` is not
   verified on macOS).
6. The real update, performed and recorded by a person: on a machine with
   an install of 1.0.0-beta.7 made by the apb installer, run `apb
   self-update --check` (it reports the update), then `apb self-update`,
   then `apb --version` (it prints `1.0.0-rc.1`) and `apb doctor` (it
   runs, and its defaults line names no reconcile failure). Record the
   date, the operating system, the version before and after and the
   output of the last two commands in the soak results. Until that
   record exists the soak is not complete. A failure is a defect of
   severity "wrong result" for item 3.
7. The cargo channel, performed and recorded like item 6: in a container
   `ubuntu:26.04` with exactly `build-essential`, `ca-certificates` and
   `curl` installed from apt and rustup's minimal stable toolchain (no
   bun, no cmake), run `cargo install --locked agentic-playbooks
   --version 1.0.0-rc.1`, then `apb --version` (it prints `apb
   1.0.0-rc.1`), `apb doctor` and `apb dashboard` (its page answers HTTP
   200 from inside the container). Record the date, the toolchain
   version and the output of the three commands in the soak results.

## Compatibility

Everything this release promises is stated in `docs/COMPATIBILITY.md`.
For installs that go back to an older release, the behaviour changes of
the 1.0 plan above name their own limits: run guards
(`wait_park`, `list_pilot`, `eval_doubles`), the `unattended:` section of
`policy.yaml`, connector manifests with an `mcp:` block, V320 and V340
definitions, and inbox wait definitions are refused or ignored by older
binaries as each line above says. Keep every apb that runs such playbooks
at this release or newer.
